# Family Health CRM — แพลตฟอร์มจัดการสุขภาพสำหรับครอบครัว

แนวคิดนี้ไม่ใช่แค่แอปบันทึกสุขภาพ แต่เป็น ระบบศูนย์กลางข้อมูลสุขภาพของสมาชิกครอบครัว (Family Health Management Platform) ที่ช่วยให้แต่ละคนจัดเก็บข้อมูลสุขภาพของตัวเอง และอนุญาตให้คนในครอบครัวหรือผู้ดูแลเข้ามาช่วยดูแลได้ตามสิทธิ์ที่กำหนด

แนวทางนี้ต่อยอดเป็นธุรกิจ SaaS ได้ โดยเฉพาะครอบครัวที่มีผู้สูงอายุ ผู้ป่วยโรคเรื้อรัง หรือมีสมาชิกที่ต้องช่วยกันดูแลสุขภาพ

## 3. ฟีเจอร์หลักที่ควรมี

ผมแนะนำแบ่งระบบเป็น 6 โมดูล แทนการสร้างทุกอย่างพร้อมกัน

A. Family & Workspace

- สร้างพื้นที่ครอบครัวหรือ Workspace
- เพิ่มโปรไฟล์พ่อ แม่ ลูก และผู้ดูแล
- เชิญสมาชิกด้วย QR Code หรือรหัสเชิญ
- กำหนดสิทธิ์แยกตามบุคคลและประเภทข้อมูล

B. Health Profile & Metrics

- ข้อมูลพื้นฐาน โรคประจำตัว และประวัติแพ้ยา
- ความดันโลหิต ชีพจร น้ำหนัก และระดับน้ำตาล
- กราฟแนวโน้มสุขภาพและบันทึกอาการ
- บันทึกวันที่ เวลา หน่วย และแหล่งที่มาของค่าที่วัด

C. Medication & Care Plan

- รายการยา ขนาดยา และเวลาที่ต้องรับประทานตามคำสั่งแพทย์
- บันทึกกินยาแล้ว ลืมกิน หรือเลื่อนเวลา
- เตือนยาและแจ้งผู้ดูแลตามการตั้งค่า
- บันทึกการเปลี่ยนแปลงแผนการดูแล

D. Medical Timeline

- ประวัติพบแพทย์และนัดหมาย
- ผลตรวจและเอกสารทางการแพทย์
- บันทึกเหตุการณ์สุขภาพตามลำดับเวลา
- สรุปข้อมูลเพื่อเตรียมตัวไปพบแพทย์

E. AI Health Assistant

- ถามตอบข้อมูลสุขภาพเบื้องต้น
- สรุปข้อมูลจากโปรไฟล์ที่ผู้ใช้มีสิทธิ์เข้าถึง
- ช่วยอธิบายแนวโน้มจากค่าที่บันทึก
- สร้างสรุปสุขภาพสำหรับนำไปปรึกษาแพทย์

F. Security & Consent

- ความยินยอมแยกตามวัตถุประสงค์
- กำหนดและเพิกถอนสิทธิ์ผู้ดูแล
- ประวัติการเข้าถึงและแก้ไขข้อมูล
- ส่งออกข้อมูลและจัดการคำขอเกี่ยวกับข้อมูลส่วนบุคคล

## 5. คู่แข่งและโอกาสในตลาด

ต้องแยกคู่แข่งออกเป็น 2 กลุ่ม เพราะระบบสำหรับศูนย์ดูแลผู้สูงอายุกับแอปสำหรับครอบครัวมีลูกค้าและรูปแบบรายได้ต่างกัน

| กลุ่มคู่แข่ง       | จุดแข็งที่ควรศึกษา                   | ช่องว่างที่ควรทดสอบ                |
| ------------------ | ------------------------------------ | ---------------------------------- |
| แอปเตือนยา         | ใช้ง่าย แก้ปัญหาเฉพาะ                | การแบ่งหน้าที่ระหว่างสมาชิก        |
| แอปติดตามสุขภาพ    | กราฟและประวัติข้อมูล                 | การรวมข้อมูลของทั้งครอบครัว        |
| ระบบดูแลผู้สูงอายุ | บันทึกงานดูแลและรายงาน               | ความเหมาะสมสำหรับครอบครัวทั่วไป    |
| ระบบคลินิก         | จัดการข้อมูลผู้ป่วยและกระบวนการรักษา | การใช้งานส่วนตัวที่ไม่ผูกกับคลินิก |

## 6. รูปแบบรายได้ที่เหมาะสม

ผมแนะนำให้ใช้โมเดล Freemium + Family Subscription คือเริ่มใช้ฟรี แล้วให้สมัครสมาชิกเมื่อครอบครัวต้องการฟีเจอร์เพิ่มเติม

จากแนวทางแพ็กเกจที่เคยวางไว้สำหรับระบบ Personal/Family Healthcare CRM สามารถนำมาใช้เป็นสมมติฐานเริ่มต้นในการทดสอบตลาดได้ดังนี้&#x20;

| แพ็กเกจ | ราคาที่วางไว้ | กลุ่มเป้าหมาย                              |
| ------- | ------------- | ------------------------------------------ |
| Free    | ฟรี           | ทดลองใช้งานและบันทึกสุขภาพพื้นฐาน          |
| Basic   | ฿179/เดือน    | ครอบครัวขนาดเล็ก                           |
| Pro     | ฿499/เดือน    | ครอบครัวที่ต้องดูแลหลายคน                  |
| Premium | ฿699/เดือน    | ครอบครัวที่ต้องการฟีเจอร์และโควตา AI เพิ่ม |

ราคาเหล่านี้เป็นราคาเสนอเพื่อทดสอบ ไม่ใช่ราคาที่พิสูจน์แล้วว่าตลาดยอมรับ ส่วนราคาโปรโมชั่นที่เคยพิจารณาคือ Basic ฿159, Pro ฿399 และ Premium ฿599 ต่อเดือน

สิ่งที่ควรทดสอบก่อนคือ ลูกค้ายอมจ่ายเพื่ออะไร ระหว่างการจัดการสมาชิกหลายคน การแจ้งเตือนผู้ดูแล การเก็บประวัติสุขภาพ หรือ AI Assistant ไม่ใช่กำหนดราคาโดยดูจากจำนวนฟีเจอร์เพียงอย่างเดียว

## 7. เทคโนโลยีและสถาปัตยกรรมที่แนะนำ

สำหรับการพัฒนาคนเดียวโดยใช้ AI Agent ช่วยเขียนโค้ด ผมแนะนำให้เริ่มด้วย Modular Monolith ไม่จำเป็นต้องแยก Microservices ตั้งแต่แรก

Flutter Mobile + Angular Web

ผู้ใช้ · สมาชิกครอบครัว · ผู้ดูแล · Admin

Laravel 13 API + Sanctum

Authentication · Authorization · Validation · Audit

Health Domain

Profiles · Metrics · Medication · Timeline · Documents

AI Control Plane

Context · Safety · Routing · Cost · Evaluation

PostgreSQL + Redis + Queue + Object Storage

ข้อมูลหลัก · งานเบื้องหลัง · เอกสาร

เทคโนโลยีหลักที่เหมาะกับโครงการนี้:

- Backend: Laravel 13, Sanctum และ PostgreSQL
- Web: Angular + Tailwind CSS
- Mobile: Flutter + Riverpod + GoRouter + Dio
- Infrastructure: Docker บน VPS
- AI: ระบบรองรับหลาย Provider และหลาย Model พร้อมจัดการ API Keys, ต้นทุน และโควตาในฐานข้อมูล

ข้อกำหนดสำคัญคือ AI ต้องไม่เข้าถึงฐานข้อมูลสุขภาพโดยตรง แต่ต้องรับข้อมูลผ่าน Context Gateway ที่ตรวจสอบสิทธิ์ ความยินยอม และลดข้อมูลส่วนบุคคลก่อนส่งไปยังโมเดล

## 8. MVP ที่ควรสร้างก่อน

อย่าเริ่มด้วยระบบ AI ทางการแพทย์เต็มรูปแบบ ให้เริ่มจากฟังก์ชันที่สร้างประโยชน์ได้โดยไม่ต้องพึ่ง AI ก่อน

1. Account & Workspace: สมัครสมาชิก เข้าสู่ระบบ และสร้างพื้นที่ครอบครัว
2. Member & Permission: เพิ่มสมาชิก เชิญผู้ดูแล และกำหนดสิทธิ์เข้าถึง
3. Health Records: บันทึกความดัน น้ำหนัก น้ำตาล อาการ และข้อมูลพื้นฐาน
4. Medication & Appointment: บันทึกยาและนัดหมาย พร้อมระบบเตือน
5. Health Timeline: รวมประวัติสุขภาพและเอกสารตามลำดับเวลา
6. AI Summary: ให้ AI สรุปเฉพาะข้อมูลที่ได้รับอนุญาต พร้อมข้อจำกัดและการส่งต่อผู้เชี่ยวชาญเมื่อจำเป็น

ด้านความปลอดภัย ต้องออกแบบตั้งแต่เริ่มต้น เพราะข้อมูลสุขภาพเป็นข้อมูลส่วนบุคคลที่มีความอ่อนไหวภายใต้ PDPA และการเข้าถึงข้อมูลของสมาชิกครอบครัวต้องมีฐานทางกฎหมายและการควบคุมสิทธิ์ที่เหมาะสม&#x20;

## 9. แผนตรวจสอบตลาดก่อนสร้างจริง

ผมเสนอให้ใช้เวลา 2 สัปดาห์ตอบคำถาม 3 ข้อนี้

- มีครอบครัวที่มีปัญหาเรื่องการรวมข้อมูลสุขภาพและแบ่งงานดูแลจริงกี่คน?
- ปัจจุบันพวกเขาแก้ปัญหาด้วย LINE, Excel, แอปเตือนยา หรือวิธีอื่นอย่างไร?

## 4. Product Gap ที่ควรนำไปสร้างความแตกต่าง

ผมจัดลำดับตามความสำคัญต่อ MVP และความเป็นไปได้ในการสร้างคุณค่าที่แตกต่าง ไม่ใช่การจัดอันดับขนาดตลาดที่ผ่านการพิสูจน์แล้ว

Gap 1 — Family Care Coordination

ลำดับ 1

ไม่ใช่แค่แชร์ข้อมูล แต่จัดการงานดูแลร่วมกันได้ เช่น ใครพาแม่ไปโรงพยาบาล ใครรับยา ใครวัดความดัน และใครเป็นผู้รับผิดชอบติดตามผล

MVP: มอบหมายงาน สถานะงาน ผู้รับผิดชอบ กำหนดเวลา และประวัติการทำงาน

Gap 2 — Permission ที่ละเอียดและเข้าใจง่าย

ลูกคนหนึ่งอาจดูข้อมูลยาได้ แต่ไม่จำเป็นต้องดูเอกสารส่วนตัวทุกอย่างของพ่อแม่ ผู้ดูแลชั่วคราวอาจเข้าถึงข้อมูลได้เฉพาะช่วงเวลาที่ได้รับอนุญาต

MVP: สิทธิ์แยกตามบุคคล ประเภทข้อมูล บทบาท และการเพิกถอนสิทธิ์ พร้อม Audit Log

Gap 3 — Unified Health Timeline

รวมค่าความดัน น้ำตาล อาการ ยา นัดหมาย และเอกสารทางการแพทย์ตามเวลา พร้อมระบุว่าใครเป็นผู้บันทึกและข้อมูลมาจากที่ใด

MVP: Timeline ที่ค้นหาและกรองได้ พร้อมส่งออก PDF

Gap 4 — Thai-first Family Notifications

ส่งสรุปงานดูแลและการนัดหมายให้สมาชิกที่เกี่ยวข้องผ่านช่องทางที่คุ้นเคย เช่น LINE โดยไม่ส่งข้อมูลสุขภาพละเอียดเกินความจำเป็น

MVP: In-app notifications ก่อน แล้วจึงเพิ่ม LINE เมื่อยืนยันความต้องการและต้นทุนแล้ว

Gap 5 — AI Health Context

ช่วยสรุปข้อมูลย้อนหลังและเตรียมคำถามสำหรับแพทย์ โดยอ้างอิงเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์เข้าถึง

MVP: เริ่มจากสรุป Timeline และเอกสาร ไม่เริ่มด้วยการวินิจฉัยหรือปรับยาอัตโนมัติ

## 5. MVP ที่ผมแนะนำให้ล็อกขอบเขต

สำหรับการพัฒนาโดยใช้ AI Agent ผมแนะนำให้แบ่งงานออกเป็น 3 ระยะ

### Phase 1 — Core Family CRM

เริ่มก่อน

เป้าหมาย: สร้างประโยชน์ได้โดยไม่พึ่ง AI

- Account, Workspace และ Health Profiles
- Invitation, Consent และ Permission
- Health Metrics และ Medication Records
- Appointment, Timeline และ Documents
- Notifications และ Audit Log

### Phase 2 — Family Coordination

เป้าหมาย: ทำให้ครอบครัวหลายคนทำงานร่วมกันได้

- Care Tasks และผู้รับผิดชอบ
- การติดตามการกินยาและนัดหมาย
- สรุปกิจกรรมรายวัน
- ส่งออก PDF และแชร์รายงานตามสิทธิ์
- ทดสอบการแจ้งเตือนผ่าน LINE

### Phase 3 — AI Assistant

เป้าหมาย: เพิ่มมูลค่าโดยควบคุมความเสี่ยงและต้นทุน

- Context Gateway และการกรองข้อมูล
- AI สรุปประวัติสุขภาพ
- Medical Input Guard และ Risk Classification
- Provider Routing, Usage Limits และ Cost Tracking
- Evaluation และ Safety Tests

## 6. สิ่งที่ควรทำต่อก่อนเริ่มเขียนโค้ด

ยังมี 3 เรื่องที่ข้อมูลสาธารณะตอบไม่ได้ครบ ได้แก่ การใช้งานจริงของผู้ดูแลในไทย ความเต็มใจจ่ายของครอบครัว และความสะดวกของขั้นตอนเชิญสมาชิก

ผมจึงแนะนำให้ทดลองต้นแบบกับครอบครัว 10–15 ครอบครัว โดยวัดว่า

- พวกเขาใช้เวลาประสานงานดูแลกันเท่าไรในแต่ละสัปดาห์
- ปัจจุบันข้อมูลกระจายอยู่ที่ไหนบ้าง
- ฟีเจอร์ใดช่วยลดการโทรถามหรือการลืมงานได้จริง
- ยอมจ่ายรายเดือนหรือไม่ และต้องมีฟีเจอร์ใดก่อนจึงจะจ่าย

ข้อสรุป: ไม่ควรพยายามเอาชนะ CareClinic ด้วยจำนวนฟีเจอร์ หรือแข่งกับ CloudNurse ด้วยระบบจัดการสถานดูแล แต่ควรสร้างผลิตภัณฑ์ที่ทำให้ครอบครัวไทย ประสานงานดูแลพ่อแม่ได้ง่าย มีข้อมูลสุขภาพที่เชื่อถือได้ และควบคุมสิทธิ์ของแต่ละคนได้อย่างปลอดภัย

นี่คือสมมติฐานผลิตภัณฑ์ที่ควรนำไปทดสอบก่อนล็อกสถาปัตยกรรมและเริ่มให้ AI Agent สร้างระบบเต็มรูปแบบครับ

Boss ผมแนะนำให้ออกแบบ Family Care Coordination เป็น ระบบประสานงานการดูแลที่มีผู้รับผิดชอบชัดเจน มีสิทธิ์เข้าถึงตามบริบท ตรวจสอบย้อนหลังได้ และปรับเปลี่ยนตามสถานการณ์ของแต่ละครอบครัว ไม่ใช่เพียง To-do List สำหรับเตือนกินยา

หลักการสำคัญคือ ต้องแยก 4 เรื่องออกจากกันให้ชัดเจน ได้แก่

1. ใครเป็นผู้รับการดูแล — ผู้สูงอายุหรือสมาชิกที่ต้องการความช่วยเหลือ
2. ใครมีอำนาจจัดการข้อมูล — เจ้าของข้อมูล ผู้แทนที่ได้รับอนุญาต และผู้ดูแล
3. ใครรับผิดชอบงานอะไร — ผู้รับมอบหมาย ผู้ปฏิบัติงาน และผู้ตรวจสอบ
4. เกิดอะไรขึ้นจริง — สถานะงาน หลักฐาน เวลา ผู้ดำเนินการ และประวัติการเปลี่ยนแปลง

ถ้ารวมทั้ง 4 เรื่องไว้ในระบบสิทธิ์หรือสถานะเดียว จะเกิดปัญหาได้ง่าย เช่น ลูกที่ได้รับมอบหมายให้พาแม่ไปโรงพยาบาลอาจถูกตีความผิดว่าเป็นผู้มีสิทธิ์เข้าถึงข้อมูลสุขภาพทั้งหมดของแม่

## 1. สถาปัตยกรรมแนวคิดที่แนะนำ

Family Workspace

ขอบเขตสมาชิก ความสัมพันธ์ และการกำกับดูแล

Access Control

Identity · Consent · Delegation · Scope

Care Team

สมาชิก ผู้ดูแล และผู้ช่วยดูแล

Care Coordination Engine

Care Plan · Tasks · Assignment · Scheduling · Escalation

Execution

รับงาน · ลงมือทำ · บันทึกผล · ส่งต่อ

Oversight

ติดตาม · แจ้งเตือน · Audit · Reports

สถาปัตยกรรมนี้ควรเป็นส่วนหนึ่งของ Modular Monolith ใน Laravel ไม่จำเป็นต้องสร้าง Microservices แยกตั้งแต่ MVP แต่ต้องแยก Domain และกฎทางธุรกิจให้ชัด เพื่อให้พัฒนาต่อได้โดยไม่ต้องรื้อระบบภายหลัง

## 2. ออกแบบสิทธิ์ให้ยืดหยุ่น แต่ไม่เปิดช่องให้ข้อมูลรั่ว

ผมแนะนำให้ใช้ RBAC + Relationship-Based Access Control + Resource Scope ร่วมกัน

- RBAC: กำหนดบทบาทพื้นฐาน เช่น Owner, Caregiver และ Viewer
- Relationship-based: พิจารณาความสัมพันธ์กับผู้รับการดูแล เช่น ลูก ผู้ปกครอง หรือผู้ดูแลที่ได้รับมอบหมาย
- Resource scope: ระบุว่าเข้าถึงสมาชิกคนไหน ข้อมูลประเภทใด และทำอะไรได้บ้าง

อย่าใช้บทบาทอย่าง `family_admin` เป็นสิทธิ์ครอบจักรวาล เพราะการเป็นผู้ดูแลครอบครัวไม่ได้หมายความว่ามีสิทธิ์อ่านเอกสารสุขภาพทุกประเภทของทุกคน

### ตัวอย่าง Permission Matrix

| การกระทำ               | ผู้รับการดูแล       | ผู้ดูแลที่ได้รับอนุญาต           | ผู้ช่วยเฉพาะงาน       |
| ---------------------- | ------------------- | -------------------------------- | --------------------- |
| ดูข้อมูลสุขภาพ         | ตามสิทธิ์ตนเอง      | ตามขอบเขตที่อนุญาต               | เฉพาะข้อมูลที่จำเป็น  |
| แก้ไขข้อมูลสุขภาพ      | ตามสิทธิ์ตนเอง      | ตามสิทธิ์ที่ให้ไว้               | ปกติไม่อนุญาต         |
| มอบหมายงาน             | ตามบทบาท            | ตามสิทธิ์ที่ได้รับ               | ไม่ได้โดยอัตโนมัติ    |
| รับและทำงานดูแล        | ได้                 | ได้                              | เฉพาะงานที่มอบหมาย    |
| เชิญสมาชิกใหม่         | ตามสิทธิ์           | เฉพาะเมื่อได้รับอนุญาต           | ไม่ได้                |
| ให้สิทธิ์เข้าถึงข้อมูล | จัดการสิทธิ์ของตน   | เฉพาะเมื่อได้รับอำนาจอย่างชัดเจน | ไม่ได้                |
| เพิกถอนสิทธิ์          | เพิกถอนการแชร์ของตน | ตามขอบเขตอำนาจ                   | ไม่มีอำนาจเพิ่มสิทธิ์ |

ตารางนี้เป็นนโยบายตั้งต้น ไม่ใช่กฎตายตัวสำหรับทุกครอบครัว ต้องรองรับกรณีผู้เยาว์ ผู้ที่ต้องมีผู้แทนโดยชอบธรรม และผู้ที่มีข้อจำกัดในการตัดสินใจด้วย

### กฎความปลอดภัยที่ต้องบังคับใช้

1. การเป็นสมาชิก Workspace ไม่เท่ากับการได้รับสิทธิ์ดูข้อมูลสุขภาพทุกคน
2. การมอบหมายงานไม่สร้างสิทธิ์เข้าถึงข้อมูลใหม่โดยอัตโนมัติ
3. การเชิญสมาชิกต้องมีการยอมรับคำเชิญ และตรวจสอบสิทธิ์ก่อนเข้าถึงข้อมูล
4. การเพิกถอนสิทธิ์ต้องมีผลกับการเข้าถึงครั้งต่อไปทันที รวมถึงการดาวน์โหลดหรือแชร์ที่ระบบยังควบคุมได้
5. การเข้าถึงฉุกเฉิน หากมีในอนาคต ต้องมีเหตุผล ขอบเขตจำกัด ระยะเวลาหมดอายุ และ Audit Log ไม่ใช่ช่องทางข้ามระบบสิทธิ์ทั่วไป

## 3. ออกแบบ Care Task ให้ครอบคลุมงานจริง

งานดูแลไม่ควรมีแค่ชื่อและวันครบกำหนด เพราะการดูแลคนจริงมีทั้งงานที่ทำครั้งเดียว งานประจำ งานที่ต้องรอผล งานที่ต้องส่งต่อ และงานที่ไม่สามารถทำได้ตามแผน

ผมแนะนำให้แต่ละ Task มีข้อมูลอย่างน้อยดังนี้

## Care Task — โครงสร้างข้อมูล

ตัวตนและบริบท

Task ID · Workspace ID · Care Recipient ID · Care Plan ID (optional)

รายละเอียดงาน

ประเภทงาน · ชื่อ · คำอธิบาย · ความสำคัญ · เวลาเริ่ม · Deadline · Timezone

ความรับผิดชอบ

ผู้สร้าง · ผู้รับผิดชอบหลัก · ผู้ช่วย · ผู้ตรวจสอบ (optional)

การปฏิบัติงาน

สถานะ · ผลการดำเนินงาน · เวลาเริ่มและจบ · หมายเหตุ · หลักฐาน (optional)

การกำกับดูแล

กฎการแจ้งเตือน · การส่งต่อ · Audit Events · Version · Idempotency Key

### ประเภทงานที่ควรรองรับ

- `MEDICATION_SUPPORT` — งานช่วยดูแลเรื่องยา โดยอิงแผนยาที่มีอยู่
- `VITAL_MEASUREMENT` — วัดความดัน ชีพจร น้ำตาล หรือน้ำหนัก
- `APPOINTMENT` — นัดหมายหรือพาไปพบแพทย์
- `DOCUMENT_FOLLOW_UP` — ติดตามผลตรวจหรือเอกสาร
- `DAILY_CARE` — งานดูแลประจำวัน
- `FOLLOW_UP` — ติดตามอาการหรือผลจากเหตุการณ์ก่อนหน้า
- `CUSTOM` — งานเฉพาะของครอบครัว

ควรแยกประเภทงานออกจากความสำคัญและความเสี่ยง เช่น งานวัดความดันอาจเป็นงานประจำทั่วไป แต่ถ้าบุคลากรทางการแพทย์กำหนดให้ติดตามค่าที่ผิดปกติ งานนั้นอาจต้องมีขั้นตอนการส่งต่อเฉพาะ

ข้อควรระวัง: การทำเครื่องหมายว่า “กินยาแล้ว” เป็นบันทึกที่ผู้ใช้รายงาน ไม่ใช่หลักฐานทางการแพทย์ที่ยืนยันได้เสมอว่าผู้รับการดูแลได้รับยาและกินยาจริง

## 4. ใช้ State Machine แทนการเปลี่ยนสถานะอิสระ

ลูก A — ผู้ดูแลหลัก

ประสานงาน นัดหมายแพทย์ และติดตามงานที่ยังไม่เสร็จตามอำนาจที่ได้รับ

ลูก B — ผู้รับผิดชอบการเดินทาง

รับงานพาแม่ไปโรงพยาบาลและบันทึกผลการดำเนินงาน โดยไม่จำเป็นต้องมีสิทธิ์แก้ไขข้อมูลสุขภาพทั้งหมด

เพื่อให้ยืดหยุ่น ควรรองรับความสัมพันธ์ดังต่อไปนี้

- ผู้ดูแลหนึ่งคนดูแลสมาชิกได้หลายคน
- สมาชิกหนึ่งคนมีผู้ดูแลได้หลายคน
- งานหนึ่งงานมีผู้รับผิดชอบหลักหนึ่งคน และผู้ช่วยได้หลายคน
- มีผู้รับผิดชอบสำรองสำหรับงานสำคัญ
- สมาชิกสามารถปฏิเสธหรือส่งคืนงานได้ หากมีสิทธิ์และแจ้งเหตุผล
- สามารถมอบหมายงานชั่วคราวในช่วงเดินทางหรือเจ็บป่วยได้

สำหรับ MVP ผมแนะนำให้กำหนด ผู้รับผิดชอบหลักเพียงหนึ่งคนต่อ Task เพื่อหลีกเลี่ยงปัญหาที่ทุกคนคิดว่าอีกคนจะเป็นคนทำ ส่วนผู้ช่วยและผู้ติดตามสามารถมีได้หลายคน

## 6. ระบบ Recurring Tasks และ Escalation

งานประจำเป็นส่วนที่ต้องออกแบบให้ถูกต้องตั้งแต่แรก เพราะเกี่ยวข้องกับการแจ้งเตือนซ้ำ การเปลี่ยนแปลงตาราง และความเสี่ยงจากการสร้างงานซ้ำ

### Recurring Tasks

ควรแยกแม่แบบงานประจำออกจากงานที่เกิดขึ้นแต่ละครั้ง

ตัวอย่าง:

- Template: วัดความดันทุกวัน เวลา 08:00 น.
- Occurrence: งานวันที่ 18 ตุลาคม 2026 เวลา 08:00 น.
- Occurrence ถัดไป: งานวันที่ 19 ตุลาคม 2026 เวลา 08:00 น.

แต่ละ Occurrence ต้องมี Task ID และประวัติของตัวเอง เพื่อให้แก้ไขตารางในอนาคตโดยไม่เปลี่ยนข้อมูลย้อนหลัง

รองรับอย่างน้อย:

- ทุกวัน ทุกสัปดาห์ และวันที่เลือกเอง
- เขตเวลาและการเปลี่ยนเวลาในระบบ
- ข้ามครั้ง เลื่อนเวลา หยุดชั่วคราว และสิ้นสุดตาราง
- การแก้ไขเฉพาะครั้งนี้ หรือครั้งนี้และครั้งต่อไป
- ป้องกันการสร้างงานซ้ำเมื่อ Queue Retry หรือ Job ทำงานซ้ำ

สำหรับระบบนี้ควรใช้ Laravel Scheduler + Queue และสร้าง Occurrence ผ่านกลไกที่มี Unique Constraint หรือ Idempotency Key ไม่ใช่พึ่งการตรวจสอบด้วยโค้ดอย่างเดียว

### Escalation เมื่อไม่มีคนทำงาน

ถึงกำหนดงาน

แจ้งผู้รับผิดชอบหลัก

เกินเวลาที่กำหนด

ตรวจสอบประเภทงานและกฎการส่งต่อ

งานทั่วไป

แจ้งเตือนผู้ดูแลสำรอง

งานสำคัญ

แจ้งผู้ประสานงานตามแผน

ข้อสำคัญ: Escalation เป็นการแจ้งว่าระบบยังไม่มีบันทึกยืนยันการทำงาน ไม่ใช่การสรุปว่าผู้สูงอายุไม่ได้รับการดูแลจริง และไม่ควรให้ระบบส่งข้อความที่เปิดเผยข้อมูลสุขภาพเกินจำเป็น

หากมีข้อมูลที่อาจเป็นเหตุฉุกเฉินทางการแพทย์ ต้องใช้แนวทางความปลอดภัยที่แยกต่างหาก ไม่ควรใช้เพียงการแจ้งเตือนงานค้างแทนกระบวนการฉุกเฉิน

### ข้อกำหนดด้านฐานข้อมูลที่ไม่ควรละเลย

- ทุก Query ที่เกี่ยวกับข้อมูลสุขภาพต้องจำกัดขอบเขต Workspace และ Profile ตามสิทธิ์
- ใช้ Foreign Key และ Unique Constraint กับความสัมพันธ์ที่สำคัญ
- ใช้ Transaction สำหรับการมอบหมายงาน การเปลี่ยนสถานะ และการเพิกถอนสิทธิ์
- ใช้ Optimistic Locking หรือ Version Number เพื่อป้องกันการแก้ไขทับกัน
- ห้ามเก็บข้อมูลสุขภาพหรือข้อความละเอียดอ่อนไว้ใน Notification Payload และ Log โดยไม่จำเป็น
- เก็บ Audit Event แบบ Append-only ในระดับแอปพลิเคชัน และจำกัดสิทธิ์การแก้ไขย้อนหลัง
- กำหนดนโยบาย Retention, Backup, Restore และการลบข้อมูลให้สอดคล้องกับกฎหมายและวัตถุประสงค์การใช้งาน

อีกเรื่องหนึ่งที่สำคัญคือ `workspace_members` กับ `health_profiles` ต้องเป็นคนละ Entity เพราะสมาชิกที่เข้าสู่ระบบและบุคคลที่ได้รับการดูแลไม่จำเป็นต้องเป็นคนเดียวกัน

## 8. API ที่ควรออกแบบ

ควรใช้ API ที่สื่อถึง Resource และมีการตรวจสอบสิทธิ์ที่ Backend ทุกครั้ง ไม่พึ่งการซ่อนปุ่มบน Frontend

| Endpoint                                         | หน้าที่                        |
| ------------------------------------------------ | ------------------------------ |
| `GET /api/v1/workspaces/{workspace}/care-tasks`  | ดูรายการงานตามสิทธิ์           |
| `POST /api/v1/workspaces/{workspace}/care-tasks` | สร้างงาน                       |
| `POST /api/v1/care-tasks/{task}/assignments`     | มอบหมายงาน                     |
| `POST /api/v1/care-tasks/{task}/accept`          | รับงาน                         |
| `POST /api/v1/care-tasks/{task}/start`           | เริ่มงาน                       |
| `POST /api/v1/care-tasks/{task}/complete`        | บันทึกผลการทำงาน               |
| `POST /api/v1/care-tasks/{task}/block`           | แจ้งอุปสรรค                    |
| `POST /api/v1/care-tasks/{task}/reopen`          | เปิดงานใหม่ตามเงื่อนไข         |
| `GET /api/v1/care-tasks/{task}/events`           | ดูประวัติการดำเนินงานตามสิทธิ์ |

การสร้าง API แต่ละรายการควรมี Authorization Policy, Request Validation, Domain Rule, Audit Event และ Feature Test ที่เกี่ยวข้อง

สำหรับการแจ้งเตือนและงานที่ต้องทำเบื้องหลัง ควรใช้ Transactional Outbox หรือกลไกเทียบเท่าที่เชื่อถือได้ เพื่อป้องกันกรณีบันทึกงานสำเร็จแต่การแจ้งเตือนไม่ถูกส่ง หรือส่งซ้ำเมื่อระบบ Retry

## 10. ข้อสรุปเชิงสถาปัตยกรรม

ผมแนะนำให้กำหนดหลักการของ Family Care Coordination ไว้ดังนี้

หนึ่งงานมีผู้รับผิดชอบหลักหนึ่งคน

ลดปัญหางานตกหล่นจากการคิดว่าคนอื่นจะทำ

สิทธิ์เข้าถึงข้อมูลแยกจากการมอบหมายงาน

ผู้รับงานไม่จำเป็นต้องเข้าถึงข้อมูลสุขภาพทั้งหมดของสมาชิก

ทุกการเปลี่ยนแปลงสำคัญตรวจสอบย้อนหลังได้

เก็บว่าใครทำอะไร เมื่อไร เปลี่ยนจากสถานะใดเป็นสถานะใด และเพราะเหตุใด

Workflow ปรับได้ตามประเภทงาน

งานทั่วไป งานประจำ งานที่ต้องตรวจสอบ และงานที่มีความเสี่ยงไม่ควรถูกบังคับให้ใช้กฎเดียวกัน

AI เป็นผู้ช่วย ไม่ใช่ผู้ควบคุมการดูแล

AI ช่วยสรุปและแนะนำขั้นตอน แต่ไม่ควรเปลี่ยนแผนยา มอบสิทธิ์ หรือปิดงานสำคัญโดยอัตโนมัติโดยไม่มีการอนุมัติที่เหมาะสม

### ลำดับพัฒนาที่เหมาะสมที่สุด

1. วาง Domain Model, Workspace, Profile, Consent และ Authorization ให้ถูกต้องก่อน
2. สร้าง Care Task, Assignment, State Machine และ Audit Trail
3. เพิ่ม Recurring Tasks, Queue, Notifications และ Escalation
4. ทดสอบการทำงานร่วมกันของสมาชิกหลายคน รวมถึงกรณีสิทธิ์ถูกเพิกถอนและการทำงานซ้ำ
5. เพิ่ม AI Health Context หลังจากระบบข้อมูลและสิทธิ์มีความน่าเชื่อถือแล้ว

คำแนะนำสุดท้าย: อย่าเริ่มจากการเขียนหน้าจอ Task Management ก่อนออกแบบ Domain และกฎการเข้าถึงข้อมูล เพราะสิ่งที่ทำให้ผลิตภัณฑ์นี้แตกต่างและน่าเชื่อถือ ไม่ใช่แค่การมอบหมายงาน แต่คือการทำให้ทุกคนรู้ว่าต้องทำอะไร ใครรับผิดชอบ งานดำเนินไปถึงไหน และข้อมูลที่แต่ละคนเห็นนั้นได้รับอนุญาตอย่างถูกต้องหรือไม่

---

ได้ครับ และผมคิดว่าควรออกแบบ Domain Model และกฎการเข้าถึงข้อมูล (Authorization Model) ไปพร้อมกันตั้งแต่ต้น สำหรับ Family Health CRM เพราะสองส่วนนี้มีผลโดยตรงต่อความปลอดภัย ความถูกต้องของข้อมูลสุขภาพ และการรองรับสมาชิกครอบครัวกับผู้ดูแลหลายคนในอนาคต

หลักสำคัญคือ การเป็นสมาชิกครอบครัว ไม่ได้หมายความว่าจะมีสิทธิ์เห็นข้อมูลสุขภาพทุกอย่างของสมาชิกทุกคน และการได้รับมอบหมายงานดูแล ก็ไม่ควรทำให้เข้าถึงเวชระเบียนของบุคคลนั้นได้โดยอัตโนมัติ

ผมเสนอให้ออกแบบเป็น 4 ชั้นที่ทำงานร่วมกัน:

1. Domain Model — ระบบมีใครบ้าง ข้อมูลอะไร และแต่ละสิ่งมีความสัมพันธ์กันอย่างไร
2. Authorization Model — ใครทำอะไรกับข้อมูลใดได้ ภายใต้ขอบเขตและเงื่อนไขอะไร
3. Consent & Delegation — เจ้าของข้อมูลยินยอมให้ใครเข้าถึงข้อมูลส่วนใด และมอบหมายอำนาจได้นานแค่ไหน
4. Audit & Enforcement — ตรวจสอบย้อนหลังได้ว่าใครเข้าถึงหรือแก้ไขอะไร และทุก API บังคับใช้กฎเดียวกัน

ด้านล่างเป็นแบบร่างระดับสถาปัตยกรรมที่สามารถนำไปแตกเป็นเอกสาร `.ai/` และให้ AI Agent ใช้พัฒนาโปรเจกต์ต่อได้

## 1. กำหนด Domain หลักของระบบ

ผมแนะนำให้ใช้ DDD (Domain-Driven Design) + Modular Monolith + API-first โดยแบ่ง Bounded Context ตามความรับผิดชอบทางธุรกิจ ไม่ใช่แบ่งตามหน้าจอหรือประเภท CRUD

### 1.1 โครงสร้างความสัมพันธ์ของข้อมูล

Tenant

ขอบเขตองค์กรและ SaaS

Workspace

พื้นที่ครอบครัวหรือกลุ่มผู้ดูแล

Person / Health Profile

บุคคลที่รับการดูแลและข้อมูลสุขภาพของบุคคลนั้น

Health Data

Vital signs, symptoms, conditions

Care Management

Medication, appointments, tasks

Medical Records

Documents, reports, history

AI Context

ข้อมูลที่อนุญาตให้ AI ใช้

ทุก Domain อยู่ภายใต้ขอบเขต Workspace และสิทธิ์เข้าถึงที่ตรวจสอบได้

ข้อสำคัญ: `User`, `Person` และ `Health Profile` ต้องเป็นคนละแนวคิดกัน

- `User` คือบัญชีที่ใช้เข้าสู่ระบบ
- `Person` คือบุคคลที่ได้รับการดูแล ซึ่งอาจยังไม่มีบัญชี
- `Health Profile` คือข้อมูลสุขภาพที่เชื่อมโยงกับบุคคล
- `Workspace Member` คือบัญชีที่ได้รับอนุญาตให้เข้าร่วม Workspace
- `Care Relationship` คือความสัมพันธ์ในการดูแล เช่น เจ้าของข้อมูล ผู้ปกครอง หรือผู้ดูแล
- `Care Task` คือภารกิจที่มอบหมายให้ผู้ดูแล ไม่ใช่สิทธิ์เข้าถึงข้อมูลสุขภาพ

การแยกเช่นนี้ช่วยรองรับกรณีที่ลูกดูแลพ่อแม่หลายคน ผู้ดูแลคนเดียวดูแลหลายครอบครัว หรือผู้สูงอายุยังไม่มีบัญชีของตนเอง

## 3. Domain Model และ Aggregate Roots

Entity และ Aggregate ที่ควรพิจารณามีดังนี้

### Identity & Workspace

`User`, `Tenant`, `Workspace`, `WorkspaceMembership`, `Invitation`

รับผิดชอบตัวตน การเป็นสมาชิก และการเชิญเข้าร่วมพื้นที่

### Person & Access

`Person`, `HealthProfile`, `CareRelationship`, `AccessGrant`, `ConsentRecord`

ระบุเจ้าของข้อมูล ความสัมพันธ์ในการดูแล และสิทธิ์ที่ได้รับ

### Health & Care

`HealthMeasurement`, `MedicationPlan`, `MedicationRecord`, `Appointment`, `MedicalDocument`, `CarePlan`, `CareTask`

แต่ละ Aggregate ควบคุมกฎธุรกิจและการเปลี่ยนสถานะของข้อมูลตนเอง

### AI & Governance

`AIConversation`, `AIContextRequest`, `AuditEvent`, `NotificationDelivery`

แยกการอนุญาตใช้ข้อมูล AI ออกจากสิทธิ์ดูข้อมูลทั่วไป และแยก Audit ออกจากข้อมูลธุรกิจที่แก้ไขได้

กฎระดับ Domain ที่ต้องกำหนดไว้ชัดเจน เช่น

- ทุกข้อมูลที่มีขอบเขต Workspace ต้องผูกกับ Workspace ที่ถูกต้อง
- Health Profile ต้องมีเจ้าของข้อมูลที่ระบุได้ แม้เจ้าของยังไม่มีบัญชี
- การย้าย Profile ระหว่าง Workspace ต้องเป็นกระบวนการเฉพาะ ไม่ใช่แก้ `workspace_id` ได้ตามอำเภอใจ
- การบันทึกสุขภาพต้องเก็บผู้บันทึก เวลา แหล่งข้อมูล และสถานะการตรวจสอบเมื่อเกี่ยวข้อง
- การเพิกถอนสิทธิ์ต้องไม่ลบประวัติการให้ความยินยอมเดิม
- การแก้ไขหรือลบข้อมูลต้องเป็นไปตามกฎการเก็บรักษาและข้อกำหนดทางกฎหมาย ไม่ควรลบ Audit Trail ไปพร้อมกับข้อมูลธุรกิจโดยอัตโนมัติ

## 4. ออกแบบ Authorization Model

ผมแนะนำให้ใช้การควบคุมสิทธิ์แบบผสม ไม่ควรใช้ RBAC อย่างเดียว

- RBAC — Role-Based Access Control: ผู้ใช้มีบทบาทอะไร
- ReBAC — Relationship-Based Access Control: ผู้ใช้สัมพันธ์กับเจ้าของข้อมูลอย่างไร
- ABAC — Attribute-Based Access Control: เงื่อนไขของผู้ใช้ ทรัพยากร การกระทำ และบริบทเป็นอย่างไร
- Consent: มีความยินยอมที่ใช้ได้กับวัตถุประสงค์นี้หรือไม่
- Entitlement: แผนบริการอนุญาตให้ใช้ความสามารถนั้นหรือไม่
- Domain Rules: การกระทำนั้นถูกต้องตามสถานะและกฎธุรกิจหรือไม่

### 4.1 ลำดับการตัดสินใจ

### 1

ยืนยันตัวตน

ผู้ใช้หรือระบบที่ร้องขอคือใคร

### 2

ตรวจ Tenant / Workspace

ทรัพยากรอยู่ในขอบเขตที่เข้าถึงได้หรือไม่

### 3

ตรวจ Relationship และ Role

มีความสัมพันธ์และบทบาทที่รองรับการกระทำนั้นหรือไม่

### 4

ตรวจ Resource Scope

มีสิทธิ์กับ Profile และชนิดข้อมูลนี้โดยเฉพาะหรือไม่

### 5

ตรวจ Consent / Purpose

ความยินยอมครอบคลุมวัตถุประสงค์และยังมีผลหรือไม่

### 6

ตรวจ Domain Rules

สถานะและเงื่อนไขทางธุรกิจอนุญาตหรือไม่

### 7

บันทึก Audit และดำเนินการ

อนุญาตเฉพาะเมื่อผ่านเงื่อนไขที่จำเป็นทั้งหมด

ปฏิเสธโดยปริยาย (deny by default) หากเงื่อนไขบังคับข้อใดไม่ผ่าน หรือระบบตรวจสอบสิทธิ์ไม่ได้

ลำดับนี้เป็นกรอบการประมวลผล ไม่ใช่การกำหนดว่าเงื่อนไขทุกข้อจำเป็นสำหรับทุก Endpoint เช่น การดูข้อมูลทั่วไปอาจไม่ต้องตรวจ Consent เฉพาะด้าน AI แต่การส่งข้อมูลสุขภาพให้ AI ต้องผ่านเงื่อนไขการใช้ข้อมูล AI เพิ่มเติม

### 4.2 ตัวอย่างบทบาทและขอบเขต

| บทบาท                   | สิทธิ์ตั้งต้นที่แนะนำ                                                                         |
| ----------------------- | --------------------------------------------------------------------------------------------- |
| Profile Owner           | จัดการข้อมูลของตนเอง และอนุญาตให้ผู้อื่นเข้าถึงตามขอบเขตที่ระบบรองรับ                         |
| Parent / Legal Guardian | จัดการข้อมูลของผู้ที่อยู่ในความปกครองตามอำนาจที่ตรวจสอบได้                                    |
| Family Admin            | จัดการสมาชิกและงานใน Workspace แต่ไม่ได้เห็นข้อมูลสุขภาพทุกชนิดโดยอัตโนมัติ                   |
| Caregiver               | เข้าถึงข้อมูลที่ได้รับมอบหมาย และทำงานดูแลตามสิทธิ์ที่กำหนด                                   |
| Read-only Viewer        | อ่านข้อมูลบางประเภทตามขอบเขตที่อนุญาต                                                         |
| Healthcare Professional | เข้าถึงข้อมูลตามความสัมพันธ์การรักษา วัตถุประสงค์ และสิทธิ์ที่ได้รับ                          |
| Platform Support        | ไม่มีสิทธิ์อ่านข้อมูลสุขภาพเป็นค่าเริ่มต้น; การเข้าถึงเพื่อสนับสนุนต้องมีการอนุมัติและตรวจสอบ |
| Platform Admin          | จัดการระบบและการตั้งค่าที่จำเป็น ไม่ได้รับสิทธิ์ข้อมูลสุขภาพทั้งหมดโดยอัตโนมัติ               |

บทบาทข้างต้นเป็นเพียง Role Template ต้องแยก บทบาทใน Workspace ออกจาก สิทธิ์ต่อ Health Profile เสมอ

### 4.3 ตัวอย่าง Permission Matrix

สัญลักษณ์: `✓` ทำได้เมื่อผ่านขอบเขตและเงื่อนไขที่เกี่ยวข้อง, `—` ไม่มีสิทธิ์โดยค่าเริ่มต้น

| การกระทำ                  | เจ้าของ Profile        | Family Admin       | Caregiver          | Viewer        |
| ------------------------- | ---------------------- | ------------------ | ------------------ | ------------- |
| ดูข้อมูลสุขภาพ            | ✓                      | —                  | ตามสิทธิ์          | ตามสิทธิ์อ่าน |
| เพิ่มค่าความดัน           | ✓                      | —                  | ตามสิทธิ์บันทึก    | —             |
| แก้ไขความยินยอมของเจ้าของ | ✓\*                    | —                  | —                  | —             |
| มอบหมายงานดูแล            | ✓                      | ตามขอบเขตงาน       | ตามขอบเขตงาน       | —             |
| บันทึกผลการดูแล           | ✓                      | ตามสิทธิ์          | ตามสิทธิ์งาน       | —             |
| เชิญสมาชิก Workspace      | ตามนโยบาย              | ✓                  | —                  | —             |
| ส่งข้อมูลสุขภาพให้ AI     | ตาม Consent และ Policy | ไม่ได้โดยอัตโนมัติ | ไม่ได้โดยอัตโนมัติ | —             |
| ส่งออกเวชระเบียน          | ตามสิทธิ์ส่งออก        | —                  | ตามสิทธิ์เฉพาะ     | —             |

`*` เจ้าของข้อมูลต้องสามารถให้หรือถอนความยินยอมในเรื่องที่ตนมีอำนาจตามกฎหมาย ส่วนผู้ปกครองหรือผู้แทนโดยชอบธรรมต้องผ่านกฎการยืนยันอำนาจนั้นก่อน

ตารางนี้เป็นค่าเริ่มต้นสำหรับการออกแบบ ไม่ใช่การตัดสินสิทธิ์ขั้นสุดท้ายในทุกสถานการณ์

## 5. ออกแบบ Consent และ Delegation ให้แยกจากกัน

สองสิ่งนี้มีความหมายต่างกัน

Consent คือความยินยอมหรือฐานอำนาจในการประมวลผลข้อมูลตามวัตถุประสงค์ เช่น ใช้ข้อมูลสุขภาพเพื่อวิเคราะห์โดย AI

Delegation / Access Grant คือการมอบสิทธิ์ให้บุคคลอื่นดำเนินการบางอย่าง เช่น ดูค่าความดัน บันทึกผลการดูแล หรือจัดการนัดหมาย

ตัวอย่างโครงสร้างข้อมูล:

`AccessGrant`

- `id`, `workspace_id`, `profile_id`
- `granted_by`, `grantee_user_id`
- `resource_scope`, `allowed_actions`
- `purpose`, `valid_from`, `expires_at`
- `status`, `revoked_at`, `revocation_reason`

`ConsentRecord`

- `id`, `profile_id`, `consent_type`
- `purpose`, `scope`, `policy_version`
- `consenting_subject_id`, `legal_basis_type`
- `granted_at`, `withdrawn_at`
- `evidence_reference`

ควรเก็บประวัติการให้และถอนความยินยอมแบบมีเวอร์ชัน ไม่เขียนทับหลักฐานเดิม และอย่าถือว่าการยอมรับเงื่อนไขการใช้บริการเท่ากับยินยอมให้ใช้ข้อมูลสุขภาพทุกวัตถุประสงค์

สำหรับประเทศไทย ต้องออกแบบให้รองรับข้อกำหนด PDPA และข้อกำหนดที่เกี่ยวข้อง โดยเฉพาะข้อมูลสุขภาพซึ่งเป็นข้อมูลส่วนบุคคลที่มีความอ่อนไหว ทั้งนี้ รายละเอียดฐานกฎหมายและข้อยกเว้นต้องผ่านการตรวจสอบทางกฎหมายก่อนนำไปใช้จริง

## 6. กฎเฉพาะที่มักถูกมองข้าม

### การมอบหมายงานไม่ใช่การมอบสิทธิ์ข้อมูล

สมมติลูกมอบหมายให้ญาติพาพ่อไปพบแพทย์ ญาติอาจเห็นรายละเอียดนัดหมายที่จำเป็น แต่ไม่ควรได้สิทธิ์อ่านประวัติโรคทั้งหมดโดยอัตโนมัติ

### การเพิกถอนต้องมีผลจริง

เมื่อเจ้าของข้อมูลเพิกถอนสิทธิ์ ระบบต้องปฏิเสธคำขอใหม่ทันทีที่ตรวจสอบสถานะสิทธิ์แล้ว รวมถึงการเข้าถึงผ่าน API, export และ AI Context Gateway ตามขอบเขตที่เพิกถอน

การเพิกถอนไม่สามารถรับประกันว่าจะลบสำเนาที่ผู้รับดาวน์โหลดไปก่อนหน้านี้ได้ทั้งหมด จึงต้องออกแบบการส่งออกและการแชร์อย่างระมัดระวังตั้งแต่แรก

### AI ต้องได้รับข้อมูลเท่าที่จำเป็น

AI ไม่ควรเชื่อมต่อฐานข้อมูลสุขภาพโดยตรง แต่ต้องผ่าน Context Gateway ซึ่งตรวจสอบสิทธิ์ วัตถุประสงค์ Consent การลดข้อมูล และการปกปิดข้อมูลที่ไม่จำเป็นก่อนส่งให้ Provider

### Emergency Access ต้องเป็นกรณีพิเศษ

หากจะรองรับ Break-glass Access ต้องกำหนดเหตุผล ขอบเขตข้อมูล ระยะเวลาหมดอายุ การแจ้งเตือน และ Audit ที่เข้มงวด การเข้าถึงฉุกเฉินไม่ควรกลายเป็นสิทธิ์ถาวร และไม่ควรใช้ข้ามข้อกำหนดทางกฎหมายโดยอัตโนมัติ

## 7. โครงสร้างข้อมูลและการบังคับใช้ใน Laravel

หากใช้ Laravel 13, Sanctum และ PostgreSQL ตามแนวทางโครงการ ควรให้ทุกคำขอผ่าน Policy/Authorization Service ที่เป็นจุดบังคับใช้เดียวกัน พร้อม Domain Service สำหรับกฎธุรกิจ

ตัวอย่าง API:

```
GET    /api/v1/workspaces/{workspace}/profiles
GET    /api/v1/profiles/{profile}/health-measurements
POST   /api/v1/profiles/{profile}/health-measurements
GET    /api/v1/profiles/{profile}/care-tasks
POST   /api/v1/profiles/{profile}/care-tasks
POST   /api/v1/access-grants
POST   /api/v1/access-grants/{grant}/revoke
POST   /api/v1/profiles/{profile}/ai-conversations
```

ทุก Endpoint ต้องตรวจทั้งสิทธิ์และขอบเขตข้อมูลฝั่งเซิร์ฟเวอร์ ห้ามเชื่อ `workspace_id`, `profile_id`, Role หรือ Consent ที่ส่งมาจาก Client โดยไม่ตรวจสอบกับข้อมูลจริง

มาตรการที่ควรมีตั้งแต่ MVP:

- UUIDv7 สำหรับ ID ตามมาตรฐานโครงการ แต่ไม่ถือว่า UUID เป็นมาตรการควบคุมสิทธิ์
- ตรวจ Workspace/Profile scope ทุกครั้งเพื่อป้องกัน IDOR และการเข้าถึงข้ามครอบครัว
- ใช้ Foreign Key, Unique Constraints และ Transaction เพื่อรักษาความถูกต้องของข้อมูล
- ใช้ Audit Event สำหรับการอ่านหรือแก้ไขข้อมูลที่มีความเสี่ยงตามนโยบาย
- ป้องกันการแก้ไขข้อมูลพร้อมกันด้วย versioning หรือ optimistic locking เมื่อจำเป็น
- ทดสอบการเพิกถอนสิทธิ์ การหมดอายุของ Grant และการเข้าถึงจาก Session ที่ยังไม่หมดอายุ
- ไม่ใส่ข้อมูลสุขภาพหรือรายละเอียด Consent ที่ละเอียดเกินจำเป็นใน Application Logs และ Notification

## 8. ลำดับการออกแบบและพัฒนาที่แนะนำ

1. Foundation: Identity, Tenant, Workspace, Person, Health Profile และ Relationship
2. Authorization: Role, Resource Scope, Access Grant, Consent และ Policy Evaluation
3. Health Domain: Health Measurements, Medication, Appointment, Medical Records และ Timeline
4. Care Coordination: Care Plan, Task, Assignment, Recurrence, Notification และ Audit
5. AI Safety: Context Gateway, Purpose Limitation, Provider Routing, Risk Classification และ Evaluation
6. Security Verification: Permission Matrix Tests, Cross-Workspace Isolation, IDOR, Revocation และ Audit Integrity

ผมแนะนำให้ทำ Permission Matrix และชุดทดสอบสิทธิ์ก่อนพัฒนา UI จำนวนมาก เพราะถ้า Domain และ Authorization ยังไม่ชัด การแก้ย้อนหลังจะกระทบทั้ง API, Mobile, Web และ AI

สำหรับการนำไปใช้กับ AI Agent ควรแยกข้อกำหนดเหล่านี้เป็นเอกสาร เช่น `DOMAIN_ARCHITECTURE.md`, `AUTHORIZATION_ARCHITECTURE.md`, `CONSENT_ARCHITECTURE.md`, `DATA_ACCESS_MATRIX.md` และ `SECURITY_TESTING.md` โดยกำหนดให้เอกสารเหล่านี้อ้างอิงกันและห้าม Agent สร้างกฎสิทธิ์ขึ้นเองโดยไม่มีข้อกำหนดรองรับ

---

สำหรับ Family Health CRM ผมแนะนำให้จัดทำ Permission Matrix และ Authorization Test Suite เป็นข้อกำหนดบังคับก่อนเริ่มพัฒนา Feature ครับ ไม่ใช่เอกสารที่ค่อยเขียนหลังจากมี API หรือหน้าจอแล้ว

เหตุผลคือระบบนี้มีทั้งเจ้าของข้อมูลสุขภาพ สมาชิกครอบครัว ผู้ดูแล และผู้ดูแลระบบ หากกำหนดสิทธิ์ไม่ชัดเจนตั้งแต่ต้น อาจเกิดกรณีที่สมาชิกคนหนึ่งเห็นข้อมูลสุขภาพของอีกคนโดยไม่ได้รับอนุญาต หรือผู้ดูแลที่ได้รับมอบหมายงานสามารถเข้าถึงข้อมูลเกินความจำเป็น

ผมเสนอให้วางแผนเป็น 3 ส่วน:

1. Permission Matrix — ระบุว่าใครทำอะไรกับข้อมูลประเภทใดได้ ภายใต้เงื่อนไขใด
2. Authorization Rules — กำหนดกฎที่ Backend ต้องใช้ตัดสินสิทธิ์อย่างสม่ำเสมอ
3. Authorization Test Suite — ทดสอบทั้งกรณีที่ต้องอนุญาตและกรณีที่ต้องปฏิเสธ ก่อนเปิดใช้งาน Feature

หลักการสำคัญคือ Deny by Default, Least Privilege, Server-side Enforcement และ Test Every Boundary โดยเฉพาะขอบเขตระหว่าง Workspace, Health Profile, ชนิดข้อมูล และวัตถุประสงค์การใช้งาน

## 1. กำหนดมาตรฐาน Permission Matrix

ก่อนสร้าง Matrix ให้แยก 3 สิ่งที่มักถูกนำมาปะปนกัน:

- Role: ผู้ใช้มีบทบาทอะไรใน Workspace
- Permission: อนุญาตให้ทำ Action ใด
- Scope: อนุญาตให้ทำ Action นั้นกับข้อมูลของใครและส่วนใด

ตัวอย่าง: ผู้ใช้เป็น `Family Admin` ไม่ได้หมายความว่าจะอ่านประวัติสุขภาพของทุกคนได้ และ `Caregiver` ที่ได้รับมอบหมายให้บันทึกความดัน ก็ไม่ควรมีสิทธิ์แก้ไขรายการยาโดยอัตโนมัติ

### 1.1 บทบาทหลักที่แนะนำ

| Role                      | ความรับผิดชอบหลัก                                                    |
| ------------------------- | -------------------------------------------------------------------- |
| `profile_owner`           | เจ้าของข้อมูล จัดการข้อมูลของตนและมอบสิทธิ์ตามที่มีอำนาจ             |
| `legal_guardian`          | ดำเนินการแทนบุคคลที่อยู่ในความปกครอง เมื่อผ่านการตรวจสอบอำนาจ        |
| `workspace_admin`         | จัดการสมาชิก คำเชิญ และการตั้งค่า Workspace                          |
| `caregiver`               | ปฏิบัติงานดูแลตามสิทธิ์และขอบเขตที่ได้รับ                            |
| `viewer`                  | อ่านข้อมูลบางประเภทตามขอบเขตที่อนุญาต                                |
| `healthcare_professional` | เข้าถึงข้อมูลตามความสัมพันธ์การรักษา วัตถุประสงค์ และสิทธิ์ที่ได้รับ |
| `platform_support`        | สนับสนุนระบบ โดยไม่มีสิทธิ์อ่านข้อมูลสุขภาพเป็นค่าเริ่มต้น           |
| `platform_admin`          | จัดการแพลตฟอร์ม ไม่ได้รับสิทธิ์ข้อมูลสุขภาพโดยอัตโนมัติ              |

ข้อควรระวัง: บทบาทเหล่านี้ไม่ควรเป็นชุดสิทธิ์ตายตัวที่ครอบคลุมทุกกรณี ควรนำไปประกอบกับ Relationship, Resource Scope และ Consent/ฐานกฎหมายที่เกี่ยวข้อง

## 2. Permission Matrix ระดับ Feature

กำหนดรหัสสิทธิ์ที่นำไปใช้ใน Backend ได้จริง เช่น `health.measurement.read` และ `care_task.complete`

สัญลักษณ์:

- `✓` อนุญาตภายใต้ขอบเขตและเงื่อนไขที่กำหนด
- `△` อนุญาตเฉพาะเมื่อมี Grant หรือเงื่อนไขเพิ่มเติม
- `—` ไม่อนุญาตเป็นค่าเริ่มต้น

| Action                    | Owner     | Guardian  | Workspace Admin | Caregiver | Viewer |
| ------------------------- | --------- | --------- | --------------- | --------- | ------ |
| ดูข้อมูลสุขภาพ            | ✓         | △         | —               | △         | △      |
| เพิ่มค่าตรวจวัด           | ✓         | △         | —               | △         | —      |
| แก้ไขข้อมูลสุขภาพ         | ✓         | △         | —               | △         | —      |
| ดูข้อมูลยา                | ✓         | △         | —               | △         | △      |
| บันทึกผลการดูแล           | ✓         | △         | —               | △         | —      |
| จัดการ Care Task          | ✓         | △         | △               | △         | —      |
| ดูเอกสารทางการแพทย์       | ✓         | △         | —               | △         | △      |
| จัดการสมาชิก Workspace    | ตามนโยบาย | ตามนโยบาย | ✓               | —         | —      |
| มอบสิทธิ์เข้าถึงสุขภาพ    | ✓\*       | △         | —               | —         | —      |
| ถอนสิทธิ์ที่ตนมีอำนาจมอบ  | ✓\*       | △         | —               | —         | —      |
| ส่งออกข้อมูลสุขภาพ        | △         | △         | —               | △         | —      |
| ส่งข้อมูลให้ AI วิเคราะห์ | △         | △         | —               | △         | —      |

`*` ขึ้นกับอำนาจตามกฎหมายและสิทธิ์ของเจ้าของข้อมูล ส่วน `△` ไม่ได้หมายความว่าผู้ใช้สามารถให้สิทธิ์ตนเองได้ แต่หมายถึงต้องมีการตรวจเงื่อนไขเพิ่มเติม

Matrix นี้เป็นระดับ Feature เท่านั้น ต้องทำ Matrix ย่อยสำหรับ Action ที่มีความเสี่ยงสูง เช่น การแก้ไขยา การแชร์เอกสาร การส่งออก และการใช้ AI

### 2.1 แยก Permission ตาม Action ให้ละเอียด

```

```

ไม่ควรใช้ Permission กว้าง ๆ เช่น `health.manage` เพียงตัวเดียว เพราะทำให้แยกสิทธิ์อ่าน บันทึก แก้ไข และลบได้ยาก

สำหรับการแก้ไขหรือลบข้อมูลสุขภาพ ควรกำหนดนโยบาย Correction, Versioning และ Retention แยกจากการแก้ไขข้อมูลทั่วไป ไม่จำเป็นต้องเปิดสิทธิ์ลบข้อมูลดิบให้ผู้ใช้ทุกคนที่มีสิทธิ์แก้ไข

## 3. กฎการอนุญาตที่ต้องบังคับใช้

ผมแนะนำให้เขียนเป็นกฎที่ตรวจสอบได้ ไม่ปล่อยให้ AI Agent ตีความจากชื่อ Role เพียงอย่างเดียว

| Rule ID    | กฎ                                                                              |
| ---------- | ------------------------------------------------------------------------------- |
| `AUTH-001` | ปฏิเสธโดยปริยายหากไม่มี Permission ที่ตรงกับ Action                             |
| `AUTH-002` | ผู้ใช้ต้องผ่านการยืนยันตัวตนก่อนเข้าถึงข้อมูลส่วนบุคคล                          |
| `AUTH-003` | ทรัพยากรต้องอยู่ใน Tenant/Workspace ที่ผู้ใช้มีสิทธิ์เข้าถึง                    |
| `AUTH-004` | ต้องตรวจสิทธิ์ต่อ Health Profile ทุกครั้ง ไม่ใช่ตรวจแค่ Workspace               |
| `AUTH-005` | Role ไม่สามารถใช้แทน Resource Scope หรือ Access Grant ได้                       |
| `AUTH-006` | การมอบหมายงานไม่สร้างสิทธิ์อ่านข้อมูลสุขภาพโดยอัตโนมัติ                         |
| `AUTH-007` | Grant ที่หมดอายุหรือถูกเพิกถอนต้องไม่อนุญาตคำขอใหม่                             |
| `AUTH-008` | การใช้ AI ต้องผ่านกฎการเข้าถึง วัตถุประสงค์ และการประมวลผลข้อมูลที่เกี่ยวข้อง   |
| `AUTH-009` | การส่งออกข้อมูลต้องผ่าน Permission สำหรับ Export โดยเฉพาะ                       |
| `AUTH-010` | การเข้าถึงข้อมูลที่มีความเสี่ยงสูงต้องมี Audit ตามนโยบาย                        |
| `AUTH-011` | Platform Admin และ Support ไม่มีสิทธิ์ข้ามกฎโดยอัตโนมัติ                        |
| `AUTH-012` | Client ไม่สามารถกำหนด Role, Scope หรือ Consent ที่ Backend เชื่อถือได้ด้วยตนเอง |

กฎสำคัญ: การอนุญาตต้องพิจารณาจากข้อมูลจริงในระบบ ณ เวลาที่ร้องขอ ไม่ใช่จาก Role หรือ Consent ที่ Client ส่งมา

## 4. Authorization Test Suite ที่ควรมี

ควรเริ่มเขียน Test ก่อนพัฒนา Feature หลัก โดยแบ่งเป็น 6 ชุด

ชุด A — Authentication & Role

ตรวจตัวตนและบทบาท

- ผู้ใช้ที่ไม่ได้เข้าสู่ระบบเรียก API ข้อมูลสุขภาพไม่ได้
- Viewer เพิ่มหรือแก้ไขข้อมูลสุขภาพไม่ได้
- Workspace Admin จัดการสมาชิกได้ แต่ไม่ได้อ่านเวชระเบียนโดยอัตโนมัติ
- Platform Admin ไม่สามารถใช้สิทธิ์บริหารระบบเพื่อข้าม Authorization Policy

ชุด B — Tenant & Profile Isolation

ตรวจการรั่วไหลข้ามครอบครัว

- สมาชิก Workspace A อ่าน Profile ของ Workspace B ไม่ได้
- ผู้ใช้เดา UUID ของ Profile อื่นแล้วเข้าถึงไม่ได้
- การแก้ `profile_id` ใน Request ไม่ทำให้เข้าถึงข้อมูลของบุคคลอื่นได้
- API List, Search, Pagination และ Export ต้องไม่ส่งข้อมูลข้าม Scope

ชุด C — Grant, Consent & Revocation

ตรวจการมอบสิทธิ์และการถอนสิทธิ์

- Caregiver อ่านได้เฉพาะข้อมูลที่ได้รับอนุญาต
- Grant หมดอายุแล้วต้องถูกปฏิเสธ
- เพิกถอน Grant แล้ว Request ใหม่ต้องถูกปฏิเสธ
- การเป็น Admin ไม่อนุญาตให้แก้ Consent แทนเจ้าของโดยไม่มีอำนาจ
- การถอน Consent สำหรับ AI ต้องป้องกันการประมวลผลใหม่ที่อาศัยความยินยอมนั้น เมื่อไม่มีฐานกฎหมายอื่นรองรับ

ชุด D — Care Task & Workflow

ตรวจสิทธิ์กับสถานะงาน

- ผู้ที่ไม่ใช่ผู้รับผิดชอบหรือผู้มีสิทธิ์จัดการ ไม่สามารถ Complete Task ได้
- ผู้รับงานไม่สามารถแก้ไขข้อมูลสุขภาพที่อยู่นอกขอบเขตงาน
- เปลี่ยนสถานะงานผิดลำดับแล้วต้องถูกปฏิเสธ
- การส่งงานต่อไม่ทำให้ผู้รับงานใหม่ได้สิทธิ์กว้างเกินที่กำหนด

ชุด E — AI & Data Export

ตรวจเส้นทางข้อมูลที่ออกจากระบบ

- AI ไม่ได้รับข้อมูลของ Profile ที่ผู้ร้องขอไม่มีสิทธิ์เข้าถึง
- Context Gateway ตัดข้อมูลที่อยู่นอก Scope ก่อนส่งให้ Provider
- ผู้ไม่มี Export Permission ไม่สามารถดาวน์โหลดรายงานได้
- การสร้างรายงานเบื้องหลังต้องตรวจสิทธิ์และสถานะการอนุญาตอีกครั้งก่อนส่งมอบไฟล์

ชุด F — Audit, Concurrency & Failure

ตรวจสอบย้อนหลังและกรณีผิดปกติ

- การอ่านหรือแก้ไขข้อมูลสำคัญถูกบันทึกตามนโยบาย
- การปฏิเสธสิทธิ์ไม่ทำให้เกิดการเปลี่ยนแปลงข้อมูล
- Request พร้อมกันขณะเพิกถอนสิทธิ์ต้องไม่สร้างช่องทางข้ามกฎ
- Queue Job ที่ทำงานซ้ำต้องไม่ทำให้เกิดการแชร์หรือส่งข้อมูลซ้ำโดยไม่ได้รับอนุญาต
- Audit ต้องไม่เก็บข้อมูลสุขภาพละเอียดเกินจำเป็น และผู้ใช้ทั่วไปแก้ไข Audit ไม่ได้

## 5. ตัวอย่าง Test Cases ที่ควรเขียนจริง

แนะนำให้ใช้รูปแบบ Given–When–Then เพื่อให้ Developer และ AI Agent เข้าใจเงื่อนไขเดียวกัน

| Test ID  | Given                                   | When                               | Expected                        |
| -------- | --------------------------------------- | ---------------------------------- | ------------------------------- |
| `AT-001` | ไม่ได้ Login                            | อ่าน Profile                       | `401 Unauthorized`              |
| `AT-002` | User A ไม่มีสิทธิ์ Profile B            | อ่าน Profile B                     | ปฏิเสธ ไม่เปิดเผยข้อมูล         |
| `AT-003` | Caregiver มีสิทธิ์บันทึกความดัน         | สร้าง Measurement                  | สำเร็จ                          |
| `AT-004` | Caregiver มีสิทธิ์บันทึกความดันเท่านั้น | แก้ไข Medication Plan              | ปฏิเสธ                          |
| `AT-005` | Grant ถูกเพิกถอนแล้ว                    | อ่านข้อมูลที่เคยเข้าถึงได้         | ปฏิเสธ                          |
| `AT-006` | Workspace Admin ไม่มี Health Grant      | Export เวชระเบียน                  | ปฏิเสธ                          |
| `AT-007` | มีสิทธิ์อ่าน แต่ไม่มีสิทธิ์ใช้ AI       | ส่งข้อมูลไป AI                     | ปฏิเสธ                          |
| `AT-008` | Task มอบหมายให้ User A                  | User B Complete Task               | ปฏิเสธ เว้นแต่มีสิทธิ์เพิ่มเติม |
| `AT-009` | Profile อยู่ใน Workspace A              | เปลี่ยน Request ให้ชี้ Workspace B | ปฏิเสธ                          |
| `AT-010` | ผู้ใช้ไม่มี Export Permission           | ขอไฟล์รายงานผ่าน URL ที่คาดเดาได้  | ปฏิเสธ                          |
| `AT-011` | Grant หมดอายุ                           | ส่ง Request ใหม่                   | ปฏิเสธ                          |
| `AT-012` | ผู้ใช้มีสิทธิ์อ่าน แต่ไม่มีสิทธิ์แก้ไข  | แก้ข้อมูลผ่าน API                  | ปฏิเสธและไม่มีข้อมูลเปลี่ยนแปลง |

รหัส HTTP เป็นตัวอย่างสำหรับแนวทาง API: ใช้ `401` เมื่อยังไม่มีการยืนยันตัวตน และอาจใช้ `403` หรือ `404` สำหรับการปฏิเสธการเข้าถึงตามนโยบายการไม่เปิดเผยการมีอยู่ของทรัพยากร ควรเลือกให้สม่ำเสมอทั้งระบบ

## 6. วิธีจัด Test Suite ใน Laravel

โครงสร้างที่แนะนำ:

```
tests/
├── Unit/
│   └── Domain/
│       ├── Authorization/
│       │   ├── PermissionEvaluatorTest.php
│       │   ├── AccessGrantTest.php
│       │   └── ConsentPolicyTest.php
│       └── CareCoordination/
│           └── CareTaskTransitionTest.php
├── Feature/
│   └── Authorization/
│       ├── AuthenticationTest.php
│       ├── WorkspaceIsolationTest.php
│       ├── HealthProfileAccessTest.php
│       ├── MeasurementAuthorizationTest.php
│       ├── MedicationAuthorizationTest.php
│       ├── CareTaskAuthorizationTest.php
│       ├── GrantRevocationTest.php
│       ├── AIContextAuthorizationTest.php
│       ├── ExportAuthorizationTest.php
│       └── AuditAuthorizationTest.php
└── Security/
    ├── IDORTest.php
    ├── MassAssignmentTest.php
    └── CrossTenantAccessTest.php
```

- Unit Tests: ทดสอบกฎ Domain และ Permission Evaluator โดยไม่พึ่ง HTTP
- Feature Tests: ทดสอบ API จริงผ่าน Middleware, Policies, Validation และ Database
- Security Tests: ทดสอบการโจมตี เช่น IDOR, Mass Assignment และการข้าม Workspace
- Integration Tests: ทดสอบ Queue, AI Gateway, Export และการเพิกถอนสิทธิ์ขณะมีงานเบื้องหลัง

ใช้ Database ที่ตรงกับสภาพแวดล้อมจริง โดยเฉพาะ PostgreSQL หากเป็นฐานข้อมูลเป้าหมาย เพราะพฤติกรรม Transaction, Constraint และ Concurrency บางอย่างอาจต่างจาก SQLite

## 8. ลำดับที่ผมแนะนำให้ทำจริง

1. เขียน `PERMISSION_CATALOG.md` เพื่อกำหนด Permission ทุกตัว
2. เขียน `DATA_ACCESS_MATRIX.md` เพื่อระบุ Role × Action × Resource × Scope
3. เขียน `AUTHORIZATION_RULES.md` เพื่อกำหนดกฎกลางและข้อยกเว้น
4. เขียน `AUTHORIZATION_TEST_PLAN.md` เพื่อผูก Rule แต่ละข้อเข้ากับ Test ID
5. ให้ AI Agent สร้าง Test และโครง Authorization Service ก่อนสร้าง Health API
6. พัฒนา Feature โดยต้องผ่าน Test ที่เกี่ยวข้องก่อน Merge

สำหรับระบบนี้ ผมจะไม่เริ่มจากการสร้าง Role และหน้า Admin ก่อน แต่จะเริ่มจาก Permission Catalog + Data Access Matrix + Test Plan แล้วใช้ทั้งสามเป็นข้อกำหนดกลางของ Backend, Web, Mobile และ AI Gateway เพื่อป้องกันไม่ให้แต่ละส่วนตีความสิทธิ์ไม่ตรงกัน&#x20;

## กฎสำคัญที่ตรึงไว้ใน Baseline

- สมาชิก Workspace ไม่ได้สิทธิ์เข้าถึงข้อมูลสุขภาพทุกคนโดยอัตโนมัติ
- Workspace Admin ไม่มีสิทธิ์อ่านเวชระเบียนโดยอัตโนมัติ
- การมอบหมาย Care Task ไม่ได้มอบสิทธิ์อ่านข้อมูลสุขภาพ
- สิทธิ์อ่าน แก้ไข ส่งออก แชร์ และส่งข้อมูลให้ AI ต้องแยกจากกัน
- ผู้ปกครองหรือผู้แทนต้องผ่านการตรวจสอบอำนาจ
- การเพิกถอนสิทธิ์ต้องมีผลกับคำขอใหม่ งานเบื้องหลัง และการส่งมอบไฟล์ตามนโยบาย
- ทุก Permission ที่เปิดใช้ต้องเชื่อมโยงกับ Matrix และชุดทดสอบ
- การเปลี่ยนกฎต้องปรับเอกสารที่เกี่ยวข้องและ Test พร้อมกัน

ข้อจำกัดสำคัญ: Frozen for Implementation หมายถึงตรึงเป็นฐานสำหรับการพัฒนา ไม่ได้หมายความว่าได้รับการรับรองทางกฎหมายหรือพร้อมใช้งานจริงแล้ว ขั้นถัดไปควรตรวจสอบโครงสร้างเอกสารและทบทวนประเด็นที่ยังต้องตัดสินใจ ก่อนเริ่มสร้าง Authorization Service ใน Laravel ครับ

สำหรับแอป Family Health CRM ที่เรากำลังออกแบบอยู่ ผมมองว่าส่วน CRM ควรเป็นหนึ่งในแกนหลักของระบบ ไม่ใช่เพียงหน้าจัดเก็บชื่อ เบอร์โทรศัพท์ หรือลิสต์สมาชิกครอบครัว แต่เป็นระบบที่ช่วยจัดการ ข้อมูลบุคคล ความสัมพันธ์ในครอบครัว การดูแลผู้ป่วย การติดตามงาน และความต่อเนื่องในการดูแลสุขภาพ โดยทำงานร่วมกับระบบจัดเก็บข้อมูลสุขภาพและระบบ AI อย่างมีขอบเขตชัดเจน

สิ่งสำคัญที่สุดคือ ต้องออกแบบให้เป็น Healthcare CRM ไม่ใช่นำ CRM สำหรับงานขายมาเปลี่ยนชื่อเป็นระบบสุขภาพ เพราะวัตถุประสงค์ ข้อมูล และข้อกำหนดด้านสิทธิ์การเข้าถึงแตกต่างกันมาก

# 1. CRM ในแอปนี้มีหน้าที่อะไร?

CRM ย่อมาจาก Customer Relationship Management แต่ในแอปสุขภาพของเรา คำว่า Customer ไม่ได้หมายถึงลูกค้าที่เราต้องขายสินค้าให้เป็นหลัก แต่หมายถึงบุคคลและความสัมพันธ์ที่เกี่ยวข้องกับการดูแลสุขภาพ เช่น ผู้สูงอายุ สมาชิกครอบครัว ผู้ดูแล และทีมดูแลสุขภาพที่ได้รับอนุญาต

CRM จึงควรตอบคำถามสำคัญได้ว่า

- เรากำลังดูแลใคร และบุคคลนั้นมีข้อมูลติดต่ออะไรบ้าง?
- บุคคลนี้เป็นสมาชิกของครอบครัวหรือ Workspace ใด?
- ใครมีหน้าที่ดูแลบุคคลนี้ และมีอำนาจทำอะไรได้บ้าง?
- งานที่ต้องติดตามมีอะไร ใครเป็นผู้รับผิดชอบ และกำหนดเวลาเมื่อไร?
- เคยมีการติดต่อ นัดหมาย ติดตาม หรือดำเนินการอะไรไปแล้วบ้าง?
- เรื่องใดกำลังรอการดำเนินการ และเรื่องใดเสร็จสิ้นแล้ว?
- ระบบสามารถแจ้งเตือนหรือช่วยให้ครอบครัวประสานงานกันได้อย่างไร?
- ข้อมูลแต่ละรายการเปิดเผยให้ใครเห็นได้บ้าง และมีเหตุผลหรืออำนาจใดรองรับ?

เป้าหมายไม่ใช่แค่เก็บข้อมูลให้ครบ แต่ต้องช่วยให้การดูแลดำเนินต่อได้อย่างเป็นระบบ ลดการลืมนัด ลดงานตกหล่น และป้องกันการเปิดเผยข้อมูลสุขภาพแก่บุคคลที่ไม่มีสิทธิ์

# 2. CRM แตกต่างจากระบบข้อมูลสุขภาพอย่างไร?

นี่เป็นการแบ่งขอบเขตที่ควรตัดสินใจตั้งแต่ต้น เพราะถ้ารวมทุกอย่างไว้ใน CRM โดยไม่มีเส้นแบ่งชัดเจน ในอนาคตระบบจะซับซ้อนมากและตรวจสอบสิทธิ์ได้ยาก

## CRM Domain

ดูแลความสัมพันธ์ การประสานงาน และกระบวนการติดตาม

- ข้อมูลบุคคลและช่องทางติดต่อ
- สมาชิกครอบครัวและความสัมพันธ์
- ผู้ดูแลและการมอบหมายอำนาจ
- ประวัติการติดต่อและเหตุการณ์ใน Timeline
- งานติดตามและการนัดหมาย
- การแจ้งเตือนและการประสานงาน

## Health Record Domain

ดูแลข้อมูลสุขภาพจริงและประวัติทางการแพทย์

- ความดันโลหิต น้ำตาล และชีพจร
- รายการยาและประวัติการใช้ยา
- อาการและประวัติสุขภาพ
- โรคประจำตัวและการแพ้ยา
- ผลตรวจและข้อมูลจากอุปกรณ์สุขภาพ
- ข้อมูลการประเมินหรือคำแนะนำทางการแพทย์

## Authorization & Consent Domain

ควบคุมว่าใครเข้าถึงข้อมูลอะไรได้ และภายใต้เงื่อนไขใด

- Permissions และขอบเขตข้อมูล
- ความสัมพันธ์ที่ได้รับการยืนยัน
- สิทธิ์ที่ได้รับมอบหมายและวันหมดอายุ
- Consent และฐานอำนาจทางกฎหมายที่เกี่ยวข้อง
- การเพิกถอนสิทธิ์และ Audit Log

ตัวอย่างเช่น CRM อาจมีรายการว่า “คุณแม่มีนัดติดตามผลวันที่ 28 ตุลาคม” ส่วนรายละเอียดผลตรวจจะอยู่ใน Health Record Domain

CRM อาจแสดงลิงก์ไปยังรายละเอียดผลตรวจได้ แต่ผู้ใช้ต้องผ่านการตรวจสิทธิ์ของข้อมูลผลตรวจนั้นอีกครั้ง ไม่ใช่เพียงมีสิทธิ์อ่าน Timeline แล้วจะอ่านผลตรวจได้ทั้งหมด

หลักการ: CRM ทำหน้าที่ประสานงานและเชื่อมโยงข้อมูล แต่ไม่ได้เป็นช่องทางลัดเพื่อเข้าถึงข้อมูลสุขภาพทั้งหมด

# 3. โมดูล CRM ที่ควรมีในแอป

ผมแนะนำให้แบ่งออกเป็นโมดูลที่มีหน้าที่ชัดเจน ดังนี้

## 3.1 Workspace & Family Management

โมดูลนี้ดูแลพื้นที่ใช้งานของครอบครัวหรือกลุ่มผู้ดูแล

ตัวอย่าง Workspace:

- ครอบครัว A
- บ้านของคุณแม่
- ครอบครัว B
- ทีมดูแลผู้ป่วยที่ได้รับอนุญาต

Workspace เป็นขอบเขตสำหรับจัดการสมาชิก การตั้งค่า และการประสานงาน ไม่ได้หมายความว่าสมาชิกทุกคนสามารถเปิดอ่านข้อมูลสุขภาพของทุกคนใน Workspace ได้

ความสามารถที่ควรมี:

| ความสามารถ          | รายละเอียด                                            |
| ------------------- | ----------------------------------------------------- |
| สร้าง Workspace     | สร้างพื้นที่ครอบครัวหรือพื้นที่ดูแล                   |
| เชิญสมาชิก          | เชิญผ่าน QR Code, Invitation Code หรือช่องทางที่กำหนด |
| จัดการสมาชิก        | เพิ่ม ระงับ หรือถอนสมาชิกตามสิทธิ์                    |
| กำหนดบทบาท          | Owner, Workspace Admin, Member เป็นต้น                |
| ดูสถานะคำเชิญ       | Pending, Accepted, Expired, Revoked                   |
| จัดการการเป็นสมาชิก | วันที่เข้าร่วม วันที่ออก และผู้ดำเนินการ              |
| แยกพื้นที่          | ป้องกันข้อมูลข้าม Workspace โดยไม่ได้รับอนุญาต        |

### ตัวอย่างสำคัญ

ลูกสาวเป็น Workspace Admin จึงสามารถจัดการคำเชิญและสมาชิกในครอบครัวได้ แต่ไม่ได้หมายความว่าลูกสาวจะมีสิทธิ์อ่านผลตรวจ รายการยา หรือข้อมูลส่วนตัวทั้งหมดของคุณแม่โดยอัตโนมัติ

การเข้าถึงข้อมูลสุขภาพต้องพิจารณาสิทธิ์แยกต่างหาก

## 3.2 Person & Contact Management

โมดูลนี้เป็นทะเบียนบุคคลและข้อมูลติดต่อหลักของระบบ

ข้อมูลที่อาจจัดเก็บ ได้แก่

- ชื่อและชื่อที่ต้องการให้เรียก
- วันเกิดหรือช่วงปีเกิดตามความเหมาะสม
- เบอร์โทรศัพท์และอีเมล
- ภาษาที่ต้องการใช้
- ช่องทางติดต่อที่สะดวก
- ผู้ติดต่อฉุกเฉิน
- สถานะการใช้งานบัญชี
- สถานะการยืนยันตัวตน
- ความสัมพันธ์กับ Workspace
- ข้อมูลการตั้งค่าการแจ้งเตือน

ต้องแยกแนวคิด 3 อย่างออกจากกันให้ชัดเจน:

1. User Account — บัญชีที่ใช้เข้าสู่ระบบ
2. Person — ตัวบุคคลที่ระบบรู้จัก
3. Health Profile — ข้อมูลสุขภาพที่ผูกกับบุคคลนั้น

ทั้งสามสิ่งไม่จำเป็นต้องเป็นหนึ่งเดียวกันเสมอไป

ตัวอย่างเช่น คุณแม่อาจมี Health Profile อยู่ในระบบ แต่ยังไม่มีบัญชีสำหรับเข้าสู่ระบบ ลูกสาวอาจเป็นผู้ช่วยจัดตั้งโปรไฟล์โดยไม่มีสิทธิ์เปิดดูข้อมูลทุกประเภทของคุณแม่

การแยกเช่นนี้ยังช่วยรองรับกรณีที่บุคคลหนึ่งมีความสัมพันธ์กับหลาย Workspace หรือมีการเปลี่ยนผู้ดูแลในอนาคต

## 3.3 Relationship Management

นี่เป็นโมดูลสำคัญของ Healthcare CRM เพราะระบบต้องรู้ว่าบุคคลต่าง ๆ เกี่ยวข้องกันอย่างไร ไม่ใช่เพียงใครอยู่ในรายชื่อสมาชิก

ความสัมพันธ์ที่อาจรองรับ ได้แก่

- พ่อ แม่ ลูก
- คู่สมรส
- พี่น้อง
- ญาติ
- ผู้ดูแลที่ไม่ใช่ญาติ
- ผู้แทนที่ได้รับมอบอำนาจ
- ผู้ติดต่อฉุกเฉิน
- ผู้ดูแลหลักและผู้ดูแลสำรอง

แต่ต้องแยก ความสัมพันธ์ทางครอบครัว ออกจาก อำนาจในการเข้าถึงข้อมูล

| ความสัมพันธ์หรือสถานะ          | สิ่งที่บอกระบบ                 | สิ่งที่ไม่ได้รับโดยอัตโนมัติ     |
| ------------------------------ | ------------------------------ | -------------------------------- |
| ลูกสาว                         | ความสัมพันธ์กับคุณแม่          | สิทธิ์อ่านข้อมูลสุขภาพทั้งหมด    |
| ผู้ติดต่อฉุกเฉิน               | ช่องทางติดต่อกรณีฉุกเฉิน       | สิทธิ์เปิดประวัติการรักษา        |
| ผู้ดูแลหลัก                    | บทบาทในการประสานงาน            | อำนาจทำทุกอย่างแทนผู้ป่วย        |
| ผู้รับมอบอำนาจที่ผ่านการยืนยัน | ขอบเขตอำนาจตามหลักฐานและนโยบาย | สิทธิ์เกินขอบเขตที่ได้รับ        |
| ผู้ทำงานติดตาม                 | งานที่ได้รับมอบหมาย            | สิทธิ์เข้าถึงข้อมูลสุขภาพทั้งหมด |

ตัวอย่างเช่น บุคคล A เป็นลูกสาวของคุณแม่ แต่คุณแม่อาจอนุญาตให้ลูกสาวดูข้อมูลความดันโลหิตและช่วยจัดการนัดหมาย โดยไม่อนุญาตให้เปิดดูบันทึกสุขภาพบางประเภท

ระบบจึงต้องจัดการทั้งความสัมพันธ์และสิทธิ์ที่แยกจากกัน

## 3.4 Caregiver & Delegation Management

โมดูลนี้ดูแลว่าบุคคลใดได้รับอนุญาตให้ช่วยดูแลใคร และทำอะไรได้บ้าง

ข้อมูลที่ควรมีในการมอบหมายสิทธิ์ เช่น

- ผู้ให้สิทธิ์
- ผู้รับสิทธิ์
- บุคคลเจ้าของข้อมูลที่เกี่ยวข้อง
- ขอบเขตการดำเนินการ
- ประเภทข้อมูลที่เข้าถึงได้
- วันเริ่มต้นและวันสิ้นสุด
- สถานะการยืนยัน
- สถานะการเพิกถอน
- ข้อจำกัดหรือเงื่อนไขการใช้สิทธิ์
- หลักฐานหรือที่มาของอำนาจที่เกี่ยวข้อง
- ประวัติการเปลี่ยนแปลง

ตัวอย่างสิทธิ์ที่อาจมอบหมาย:

- ดูข้อมูลสุขภาพบางหมวด
- บันทึกค่าความดันโลหิตแทนเจ้าของโปรไฟล์
- ช่วยจัดการนัดหมาย
- จัดการรายการเตือนความจำ
- ดูงานดูแลที่ได้รับมอบหมาย
- รับการแจ้งเตือนในขอบเขตที่อนุญาต

ต้องแยกสิทธิ์ในการอ่าน การเพิ่ม การแก้ไข การส่งออก และการแชร์ข้อมูลออกจากกัน ไม่ควรให้สิทธิ์กว้างเกินความจำเป็น

การมีชื่อเป็นผู้ดูแลเพียงอย่างเดียวไม่ถือเป็นหลักฐานว่ามีอำนาจตามกฎหมายในการตัดสินใจแทนผู้ป่วยทุกเรื่อง

## 3.5 Care Timeline & Interaction History

นี่คือหนึ่งในส่วนที่ทำให้ CRM มีประโยชน์กว่าทะเบียนสมาชิกทั่วไป

Timeline รวมเหตุการณ์ที่เกี่ยวข้องกับการดูแลไว้ตามลำดับเวลา เช่น

- เพิ่มสมาชิกเข้าระบบ
- เชิญผู้ดูแล
- เปลี่ยนแปลงสิทธิ์
- จัดเตรียมนัดหมาย
- โทรติดตามหรือบันทึกการติดต่อ
- สร้างงานติดตามสุขภาพ
- บันทึกว่าได้ช่วยเหลือในเรื่องใด
- ได้รับแจ้งเตือนและดำเนินการต่อ
- เชื่อมโยงไปยังเหตุการณ์สุขภาพที่เกี่ยวข้อง

แต่ Timeline ไม่ควรเก็บข้อมูลทั้งหมดซ้ำซ้อนอีกชุดหนึ่ง

ตัวอย่าง:

| เหตุการณ์ใน CRM             | ข้อมูลต้นทางที่เกี่ยวข้อง        |
| --------------------------- | -------------------------------- |
| นัดติดตามผลวันที่ 28 ต.ค.   | Appointment                      |
| ได้รับมอบหมายให้ตรวจความดัน | Care Task                        |
| วัดความดันแล้ว              | Health Measurement               |
| บันทึกการติดต่อกับผู้ดูแล   | Interaction Log                  |
| ผู้ดูแลถูกเพิกถอนสิทธิ์     | Delegation / Authorization Audit |

แนวทางนี้ทำให้ระบบสามารถเชื่อมโยงข้อมูลที่เกี่ยวข้องกันได้ โดยยังคงแยกการจัดเก็บและสิทธิ์เข้าถึงตามประเภทข้อมูล

ข้อควรระวัง: หาก Timeline แสดงข้อมูลสุขภาพ ระบบต้องตรวจสิทธิ์ของข้อมูลแต่ละรายการก่อนแสดงผล ห้ามถือว่าผู้ที่อ่าน Timeline ได้จะอ่านเหตุการณ์และรายละเอียดทุกอย่างใน Timeline ได้ด้วย

## 3.6 Care Task & Follow-up Management

โมดูลนี้ช่วยให้ครอบครัวและผู้ดูแลรู้ว่าอะไรต้องทำ ใครรับผิดชอบ และเมื่อใดต้องดำเนินการ

ตัวอย่างงาน:

- ช่วยคุณแม่วัดความดันในวันพรุ่งนี้
- ตรวจสอบว่ามีการรับประทานยาตามแผนที่บันทึกไว้หรือไม่
- เตรียมเอกสารก่อนไปพบแพทย์
- ติดตามหลังการนัดหมาย
- ติดต่อผู้ดูแลหลักเพื่อยืนยันการดำเนินการ
- ตรวจสอบว่าอุปกรณ์สุขภาพยังส่งข้อมูลตามปกติ

สถานะงานอาจประกอบด้วย

`Open → In Progress → Waiting → Completed`

และอาจมีสถานะ `Cancelled` หรือ `Overdue` สำหรับงานที่ยกเลิกหรือล่วงเลยกำหนด

แต่ละงานควรมีข้อมูลอย่างน้อยดังนี้

| ฟิลด์               | ความหมาย                                    |
| ------------------- | ------------------------------------------- |
| Task ID             | รหัสงาน                                     |
| Subject             | หัวข้องาน                                   |
| Related Person      | บุคคลที่เกี่ยวข้อง                          |
| Assigned To         | ผู้รับผิดชอบ                                |
| Due At              | กำหนดเวลา                                   |
| Status              | สถานะ                                       |
| Priority            | ระดับความสำคัญ                              |
| Created By          | ผู้สร้างงาน                                 |
| Completion Evidence | หลักฐานหรือรายละเอียดเมื่อทำเสร็จ ถ้าจำเป็น |
| Visibility Scope    | ขอบเขตผู้มีสิทธิ์เห็นงาน                    |

จุดที่สำคัญต่อระบบสิทธิ์คือ การได้รับมอบหมายงานไม่ได้แปลว่าได้รับสิทธิ์เข้าถึงข้อมูลสุขภาพของผู้ป่วยทั้งหมด

ตัวอย่างเช่น ผู้ดูแลสำรองได้รับงานให้เตือนเรื่องนัดหมาย เขาควรเห็นรายละเอียดที่จำเป็นต่อการทำงานนั้น แต่ไม่จำเป็นต้องเห็นประวัติการแพ้ยาหรือบันทึกสุขภาพทุกหมวด

หากงานใดต้องอาศัยข้อมูลสุขภาพเฉพาะ ระบบต้องให้สิทธิ์ข้อมูลส่วนนั้นเพิ่มเติมอย่างชัดเจน

## 3.7 Appointment & Care Coordination

โมดูลนี้จัดการการประสานงานและนัดหมาย ไม่ควรถือว่าการมีนัดหมายเท่ากับการมีเวชระเบียนของการพบแพทย์ครั้งนั้น

สิ่งที่อาจมี ได้แก่

- วันและเวลานัด
- สถานพยาบาลหรือผู้ให้บริการ
- วัตถุประสงค์ของนัด
- ผู้ประสานงาน
- ผู้ที่จะไปพบแพทย์ด้วย
- สถานะการยืนยันนัด
- สถานะการเข้าร่วม
- เอกสารที่ต้องเตรียม
- งานติดตามหลังนัด
- การเลื่อนหรือยกเลิกนัด

ตัวอย่างสถานะ:

`Planned → Confirmed → Attended`

และอาจมี `Rescheduled`, `Cancelled`, `Missed` หรือ `Needs Follow-up`

เมื่อการนัดหมายเสร็จสิ้น ระบบอาจสร้างงานติดตามต่อ เช่น เตือนให้บันทึกผลตรวจ หรือให้ผู้ดูแลตรวจสอบว่ามีการดำเนินการตามคำแนะนำที่ได้รับแล้วหรือไม่

ข้อมูลทางการแพทย์ที่เกิดจากการนัดหมายควรอยู่ในส่วนข้อมูลสุขภาพที่เหมาะสม โดย CRM เชื่อมโยงอ้างอิงตามสิทธิ์ที่มีอยู่

## 3.8 Communication & Notification Management

CRM ควรรองรับการสื่อสารที่เกี่ยวข้องกับการดูแล เช่น

- การเชิญสมาชิก
- การแจ้งเตือนนัดหมาย
- การแจ้งเตือนงานที่ได้รับมอบหมาย
- การแจ้งว่างานเลยกำหนด
- การแจ้งเปลี่ยนแปลงสิทธิ์
- การยืนยันหรือยกเลิกการนัดหมาย
- การแจ้งเตือนผู้ดูแลสำรองตามกฎที่กำหนด

ในระยะเริ่มต้นอาจไม่จำเป็นต้องสร้างระบบแชตเต็มรูปแบบ แต่ควรออกแบบ Notification และการติดตามสถานะการส่งให้ดีตั้งแต่ต้น

ข้อมูลที่ใช้ส่งการแจ้งเตือนควรมีขอบเขตด้วย เช่น หน้าจอล็อกโทรศัพท์ไม่ควรแสดงรายละเอียดสุขภาพที่อ่อนไหวโดยไม่จำเป็น การแจ้งเตือนอาจเขียนว่า “มีรายการสุขภาพที่ต้องตรวจสอบ” แล้วให้ผู้ใช้เข้าสู่ระบบเพื่ออ่านรายละเอียดหลังตรวจสิทธิ์แล้ว

นอกจากนี้ การมีสิทธิ์รับแจ้งเตือนไม่ได้หมายความว่าผู้รับมีสิทธิ์เปิดดูข้อมูลต้นทางของการแจ้งเตือนเสมอไป

## 3.9 Consent & Communication Preferences

โมดูลนี้บันทึกการให้ความยินยอมและความต้องการในการติดต่อ แต่ต้องไม่รวมทุกเรื่องไว้ในช่อง `consent = true` ช่องเดียว

ข้อมูลควรแยกอย่างน้อยเป็น

- ประเภทความยินยอม
- วัตถุประสงค์
- ผู้ให้ความยินยอม
- บุคคลที่ข้อมูลเกี่ยวข้อง
- วันที่ให้ความยินยอม
- รุ่นของข้อความหรือเอกสารที่ยอมรับ
- ขอบเขตข้อมูลหรือกิจกรรมที่เกี่ยวข้อง
- สถานะการถอนความยินยอม
- หลักฐานการให้ความยินยอมตามความเหมาะสม

ขณะเดียวกัน Communication Preferences ใช้เก็บว่าผู้ใช้สะดวกให้ติดต่อผ่านช่องทางใด ภาษาอะไร และต้องการรับการแจ้งเตือนแบบใด

ทั้งสองส่วนไม่ใช่สิ่งเดียวกัน:

- การตั้งค่าว่าไม่ต้องการรับ SMS ไม่ได้แปลว่าถอนความยินยอมทุกประเภท
- การยินยอมให้รับการแจ้งเตือน ไม่ได้แปลว่ายินยอมให้ผู้ดูแลทุกคนเข้าถึงข้อมูลสุขภาพ
- การมอบสิทธิ์ในระบบ ไม่ได้ใช้แทนการพิจารณาฐานอำนาจทางกฎหมายที่จำเป็น

## 3.10 Case & Service Request Management

โมดูลนี้จัดการเรื่องที่ต้องมีผู้รับผิดชอบและติดตามจนจบ โดยไม่จำเป็นต้องเป็นปัญหาทางการแพทย์เสมอไป

ตัวอย่าง:

- สมาชิกไม่สามารถเข้าสู่ระบบ
- ต้องยืนยันตัวตนผู้ดูแล
- ต้องแก้ไขข้อมูลติดต่อ
- ต้องตรวจสอบคำเชิญที่ไม่สำเร็จ
- ต้องดำเนินการคำขอถอนสิทธิ์
- ต้องขอสำเนาข้อมูลหรือดำเนินการตามคำขอของเจ้าของข้อมูล

แต่ละ Case ควรมีผู้รับผิดชอบ สถานะ เส้นตาย ประวัติการดำเนินการ และขอบเขตผู้ที่เปิดดูได้

หากมีรายละเอียดสุขภาพอยู่ใน Case ต้องควบคุมสิทธิ์ตามความอ่อนไหวของข้อมูลนั้น ไม่ควรถือว่าผู้ดูแล Case ทุกคนเห็นข้อมูลสุขภาพได้

## 3.11 Document & Attachment Management

CRM อาจต้องรองรับเอกสารที่ใช้ประสานงาน เช่น เอกสารนัดหมาย แบบฟอร์ม หรือเอกสารยืนยันอำนาจของผู้แทน

แต่ต้องแยกประเภทเอกสารและระดับความอ่อนไหว เช่น

- เอกสารทั่วไปของ Workspace
- เอกสารยืนยันตัวตนหรืออำนาจผู้แทน
- เอกสารนัดหมาย
- เอกสารสุขภาพ
- เอกสารที่ต้องจำกัดการดาวน์โหลดหรือการแชร์

การดูไฟล์ ดาวน์โหลดไฟล์ แชร์ไฟล์ และลบไฟล์ควรเป็นคนละสิทธิ์ตามความเหมาะสม

ระบบควรตรวจสิทธิ์อีกครั้งเมื่อมีการขอดาวน์โหลด และเมื่อมีการส่งไฟล์ผ่านลิงก์ที่มีวันหมดอายุ การเพิกถอนสิทธิ์ต้องไม่ทำให้ผู้ใช้ยังเข้าถึงไฟล์ได้โดยอ้อมผ่านลิงก์เดิมโดยไม่มีข้อจำกัด

## 3.12 CRM Dashboard & Care Overview

Dashboard เป็นหน้าสรุปเพื่อช่วยให้ผู้ดูแลเห็นงานที่ต้องดำเนินการ โดยแสดงเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์เห็น

ตัวอย่างองค์ประกอบ:

- งานที่ต้องทำวันนี้
- งานเกินกำหนด
- นัดหมายที่กำลังจะมาถึง
- งานที่รอการยืนยัน
- รายการติดตามที่ยังไม่เสร็จ
- สถานะการเชิญสมาชิก
- คำขอที่รอการตรวจสอบ
- สถานะของผู้ดูแลและสิทธิ์ที่ใกล้หมดอายุ

ควรระวังไม่ใช้ Dashboard เป็นช่องทางที่รวมข้อมูลทั้งหมดแล้วแสดงให้ผู้ใช้ทุกบทบาทเห็นเหมือนกัน

ข้อมูลสรุปยังต้องผ่านการตรวจสิทธิ์ เช่น จำนวนงานติดตามอาจแสดงได้ แต่ชื่อบุคคล รายละเอียดสุขภาพ หรือผลตรวจต้องแสดงเฉพาะเมื่อมีสิทธิ์รองรับ

# 4. ผู้ใช้แต่ละประเภทควรใช้ CRM ได้อย่างไร?

ผมแนะนำให้เริ่มจากบทบาทเชิงธุรกิจที่ชัดเจน แล้วใช้ Permission Catalog ควบคุมสิทธิ์จริง แทนการให้สิทธิ์ตามชื่อ Role เพียงอย่างเดียว

| บทบาท                   | หน้าที่หลัก                                 | ขอบเขตที่ต้องระวัง                                |
| ----------------------- | ------------------------------------------- | ------------------------------------------------- |
| Profile Owner           | จัดการข้อมูลและสิทธิ์ของตนเอง               | สิทธิ์ของผู้อื่นต้องไม่เกิดขึ้นโดยอัตโนมัติ       |
| Workspace Owner         | ดูแลพื้นที่ครอบครัวและสมาชิก                | ไม่ได้สิทธิ์ข้อมูลสุขภาพของทุกคนโดยอัตโนมัติ      |
| Workspace Admin         | จัดการสมาชิก คำเชิญ และการตั้งค่า           | ไม่ใช่ผู้ดูแลสุขภาพโดยอัตโนมัติ                   |
| Caregiver               | ช่วยประสานงานตามที่ได้รับอนุญาต             | ใช้สิทธิ์เฉพาะข้อมูลและงานที่ได้รับมอบหมาย        |
| Task Assignee           | ดำเนินงานที่ได้รับมอบหมาย                   | ไม่ได้สิทธิ์เข้าถึงโปรไฟล์ทั้งหมด                 |
| Verified Representative | ดำเนินการตามอำนาจที่ได้รับการยืนยัน         | อำนาจต้องมีขอบเขตและไม่เกินหลักฐานหรือกฎที่รองรับ |
| Healthcare Professional | ให้บริการตามสิทธิ์และหน้าที่ที่ได้รับอนุญาต | ต้องมีการยืนยันตัวตนและขอบเขตการเข้าถึงแยกต่างหาก |
| Platform Support        | ช่วยเหลือด้านเทคนิค                         | ไม่ควรมีสิทธิ์ประจำในการอ่านข้อมูลสุขภาพ          |

บทบาทเหล่านี้ไม่จำเป็นต้องสร้างครบทุกบทบาทใน MVP โดยเฉพาะสิทธิ์สำหรับบุคลากรทางการแพทย์ ควรกำหนดขอบเขตแยก หากยังไม่มีรูปแบบการให้บริการที่ชัดเจน

# 5. ตัวอย่างการทำงานร่วมกันของ CRM และ Health Record

สมมติว่าคุณแม่ใช้แอปติดตามสุขภาพ ลูกสาวช่วยดูแล และมีสมาชิกอีกคนเป็นผู้ดูแลสำรอง

ขั้นที่ 1 — สร้างพื้นที่ครอบครัว

ลูกสาวสร้าง Workspace และเชิญคุณแม่ ระบบบันทึกสมาชิกและความสัมพันธ์ แต่ยังไม่ให้สิทธิ์เข้าถึงข้อมูลสุขภาพทุกประเภทโดยอัตโนมัติ

ขั้นที่ 2 — กำหนดขอบเขตการดูแล

คุณแม่หรือผู้มีอำนาจที่ผ่านการตรวจสอบ อนุญาตให้ลูกสาวอ่านข้อมูลบางหมวดและช่วยจัดการงานบางประเภท ระบบบันทึกขอบเขตและสถานะสิทธิ์

ขั้นที่ 3 — สร้างงานและติดตาม

CRM สร้างงานให้วัดความดันหรือเตรียมตัวก่อนพบแพทย์ ระบุผู้รับผิดชอบและกำหนดเวลา โดยจำกัดรายละเอียดที่ผู้รับงานมองเห็น

ขั้นที่ 4 — บันทึกข้อมูลสุขภาพ

ข้อมูลความดันที่วัดได้ถูกจัดเก็บใน Health Record Domain และเชื่อมโยงกับงานใน CRM ตามความเหมาะสม ไม่จำเป็นต้องเก็บข้อมูลซ้ำในหลายที่

ขั้นที่ 5 — ติดตามและตรวจสอบย้อนหลัง

Timeline แสดงว่ามีการสร้างงาน ดำเนินงาน และบันทึกข้อมูลเมื่อใด ส่วนการเปิดดูข้อมูลสุขภาพจริงต้องผ่านการตรวจสิทธิ์ของข้อมูลนั้น

ตัวอย่างนี้แสดงให้เห็นว่า CRM เป็นตัวประสานงานระหว่างคน งาน และข้อมูล แต่สิทธิ์เข้าถึงข้อมูลสุขภาพยังถูกควบคุมแยกตามหลักการที่เราวางไว้

# 6. ข้อมูลหลักที่ควรมีใน CRM Domain

ด้านล่างเป็นชุด Entity ที่แนะนำในระดับออกแบบโดเมน ไม่ใช่การบังคับว่าต้องสร้างตารางทั้งหมดตั้งแต่วันแรก

| Entity                      | หน้าที่                                   |
| --------------------------- | ----------------------------------------- |
| `workspaces`                | พื้นที่ครอบครัวหรือทีมดูแล                |
| `workspace_memberships`     | ความเป็นสมาชิกและบทบาทใน Workspace        |
| `persons`                   | ตัวแทนข้อมูลบุคคล                         |
| `contact_points`            | เบอร์โทรศัพท์ อีเมล และช่องทางติดต่อ      |
| `person_relationships`      | ความสัมพันธ์ระหว่างบุคคล                  |
| `caregiver_assignments`     | การมอบหมายบทบาทผู้ดูแล                    |
| `delegation_grants`         | สิทธิ์ที่บุคคลได้รับมอบหมายอย่างมีขอบเขต  |
| `interaction_logs`          | บันทึกการติดต่อหรือการประสานงาน           |
| `care_tasks`                | งานที่ต้องดำเนินการ                       |
| `task_assignments`          | ผู้รับผิดชอบงาน                           |
| `appointments`              | ข้อมูลนัดหมายและการประสานงาน              |
| `care_cases`                | กรณีที่ต้องติดตามจนจบ                     |
| `communication_preferences` | ความต้องการด้านช่องทางสื่อสาร             |
| `consent_records`           | บันทึกความยินยอมและหลักฐานที่เกี่ยวข้อง   |
| `notification_records`      | ประวัติและสถานะการแจ้งเตือน               |
| `document_references`       | ข้อมูลอ้างอิงไฟล์และขอบเขตสิทธิ์          |
| `audit_events`              | ประวัติการกระทำสำคัญ                      |
| `crm_timeline_events`       | เหตุการณ์รวมสำหรับแสดง Timeline หากจำเป็น |

มีบางสิ่งที่ควรตัดสินใจให้ชัดเจนก่อนลงมือพัฒนาจริง

หนึ่ง — อย่าฝังสิทธิ์ทั้งหมดไว้ใน Membership

`workspace_memberships` บอกว่าใครเป็นสมาชิกและมีบทบาทอะไรในพื้นที่นั้น แต่สิทธิ์อ่านข้อมูลสุขภาพของแต่ละบุคคลต้องพิจารณาจากกฎเฉพาะอีกชั้นหนึ่ง

สอง — อย่าเก็บข้อมูลสุขภาพซ้ำใน Interaction Log โดยไม่จำเป็น

หากจำเป็นต้องบันทึกข้อความอิสระ ให้ถือว่าข้อความนั้นอาจมีข้อมูลสุขภาพอ่อนไหว และกำหนดระดับการเข้าถึง การเก็บรักษา และการตรวจสอบอย่างเหมาะสม

สาม — Timeline ต้องไม่กลายเป็นช่องทางข้ามสิทธิ์

ถ้ารายการ Timeline เชื่อมไปยังข้อมูลที่มีข้อจำกัด การเข้าถึงรายละเอียดต้นทางต้องตรวจสิทธิ์ใหม่เสมอ

สี่ — ระวังการเพิกถอนสิทธิ์และงานที่ทำงานภายหลัง

งานที่อยู่ในคิว การสร้างเอกสาร และการส่งไฟล์ต้องตรวจสอบสิทธิ์ตามช่วงเวลาที่เหมาะสม ไม่ใช่ใช้สิทธิ์ที่บันทึกไว้ตั้งแต่ตอนสร้างงานโดยไม่ตรวจซ้ำ

# 7. กฎด้านสิทธิ์ที่ CRM ต้องบังคับใช้อย่างเคร่งครัด

แนวทางต่อไปนี้สอดคล้องกับ Authorization Baseline ที่เรากำลังตรึงไว้

1. Workspace membership is not health access. เป็นสมาชิกไม่ได้หมายความว่าอ่านข้อมูลสุขภาพได้
2. Admin is not automatic health access. ผู้ดูแล Workspace ไม่ได้สิทธิ์ข้อมูลสุขภาพเพียงเพราะมีบทบาท Admin
3. Task assignment is not health access. ได้รับมอบหมายงานไม่ได้หมายความว่าอ่านข้อมูลสุขภาพทั้งหมดได้
4. Relationship is not authority. การเป็นพ่อแม่ ลูก คู่สมรส หรือผู้ติดต่อฉุกเฉิน ไม่ได้ให้อำนาจเข้าถึงข้อมูลทั้งหมดโดยอัตโนมัติ
5. Read is not export or share. อ่านได้ไม่ได้แปลว่าส่งออก ดาวน์โหลด หรือแชร์ต่อได้
6. Delegated authority cannot exceed the grantor’s authority. ผู้มอบสิทธิ์ไม่สามารถมอบสิทธิ์เกินขอบเขตที่ตนมี
7. Revocation must take effect across access paths. เมื่อเพิกถอนสิทธิ์ ต้องพิจารณา API, Cache, งานในคิว และลิงก์ไฟล์ที่ออกไปแล้ว
8. Fail closed for protected health data. ถ้าระบบตรวจสอบสิทธิ์ที่จำเป็นไม่ได้ ต้องไม่เปิดเผยข้อมูลสุขภาพนั้น
9. Platform staff have no standing health data access. เจ้าหน้าที่แพลตฟอร์มไม่ควรมีสิทธิ์อ่านข้อมูลสุขภาพของผู้ใช้เป็นสิทธิ์ประจำ
10. Audit meaningful actions. การเปลี่ยนสิทธิ์ อ่านข้อมูลอ่อนไหว ส่งออก แชร์ และดำเนินการสำคัญอื่น ๆ ต้องมีการตรวจสอบย้อนหลังตามนโยบาย

นอกจากนี้ ต้องแยกการให้ความยินยอม การมีฐานอำนาจทางกฎหมาย และการอนุญาตผ่านระบบออกจากกัน ทั้งสามเรื่องเกี่ยวข้องกัน แต่ไม่ใช่สิ่งเดียวกัน

# 9. ควรพัฒนาอะไรเป็น MVP ก่อน?

ไม่แนะนำให้สร้าง CRM ทุกโมดูลพร้อมกัน เพราะจะเพิ่มทั้งจำนวนหน้าจอ รูปแบบข้อมูล และจำนวนกฎ Authorization ที่ต้องทดสอบ

ผมแนะนำให้แบ่งดังนี้

Phase 1

Core CRM Foundation

- Workspace และสมาชิก
- Person & Contact
- Relationship
- Caregiver Assignment และ Delegation
- Permission Integration
- Care Task และ Follow-up ขั้นพื้นฐาน
- Timeline ขั้นพื้นฐาน
- Audit Log
- การเพิกถอนสิทธิ์และการตรวจสอบสิทธิ์ซ้ำ

Phase 2

Care Coordination

- Appointment Management
- Notification Center
- Interaction Log
- Document Reference
- งานติดตามหลังนัด
- การประสานงานผู้ดูแลหลายคน

Phase 3

Advanced CRM & AI Integration

- Care Case Management ที่ละเอียดขึ้น
- Care Team และการประสานงานกับสถานพยาบาล
- รายงานการดำเนินงานและตัวชี้วัด
- AI ช่วยสรุป Timeline ที่ผู้ใช้มีสิทธิ์เข้าถึง
- AI ช่วยจัดลำดับงานติดตาม
- การวิเคราะห์ความต่อเนื่องของการดูแล

แม้จะพัฒนาเป็น Phase 1 แต่ไม่ควรเลื่อนการออกแบบ Permission, Consent และ Audit ไปจนถึง Phase หลัง เพราะสิ่งเหล่านี้เป็นรากฐานของข้อมูลที่เกี่ยวข้องกับสุขภาพ

## 10. สิ่งที่ไม่ควรนำมารวมใน CRM โดยตรง

เพื่อป้องกันการขยายขอบเขตจนควบคุมยาก ผมแนะนำให้แบ่งหน้าที่ดังนี้

| เรื่อง                               | Domain ที่ควรเป็นเจ้าของ   |
| ------------------------------------ | -------------------------- |
| ข้อมูลบุคคลและการติดต่อ              | CRM / Identity             |
| Workspace และสมาชิก                  | Workspace                  |
| ความสัมพันธ์และผู้ดูแล               | CRM / Relationship         |
| สิทธิ์และการมอบอำนาจ                 | Authorization              |
| ความยินยอม                           | Consent                    |
| งานติดตามและนัดหมาย                  | CRM / Care Coordination    |
| ค่าความดัน น้ำตาล ชีพจร              | Health Record              |
| โรคประจำตัวและการแพ้ยา               | Health Record              |
| ข้อมูลยาและประวัติการใช้ยา           | Medication / Health Record |
| การประเมินความเสี่ยงและ Safety Guard | AI Safety / Medical Domain |
| การสร้างและกำหนดเส้นทางคำขอ AI       | AI Orchestration           |
| การติดตามต้นทุนและโควตา AI           | AI Usage / Cost            |
| ประวัติการเข้าถึงข้อมูลสำคัญ         | Audit / Security           |

CRM ยังเชื่อมโยงข้อมูลเหล่านี้ได้ แต่ไม่ควรรับผิดชอบเก็บและตัดสินใจกฎทั้งหมดแทน Domain เจ้าของข้อมูล

แผนภาพนี้เป็นแนวแบ่งความรับผิดชอบในระดับโดเมน ไม่ได้หมายความว่าต้องมีฐานข้อมูลหรือบริการแยกกันทุกตัว

สิ่งที่ควรบังคับใช้ใน API ได้แก่

- ทุกคำขอต้องตรวจ Workspace และเจ้าของ Resource ให้ตรงกัน
- ตรวจ Permission และ Scope ก่อนอ่านหรือแก้ไขข้อมูล
- ตรวจสถานะความสัมพันธ์ การมอบสิทธิ์ การหมดอายุ และการเพิกถอน
- ตรวจ Consent หรือฐานอำนาจที่จำเป็นสำหรับกิจกรรมที่เกี่ยวข้อง
- ตรวจสิทธิ์อีกครั้งเมื่องานในคิวจะทำงานจริง หรือก่อนส่งไฟล์ให้ผู้ใช้
- ป้องกันการเดา ID เพื่อเข้าถึงข้อมูลของบุคคลอื่น
- บันทึกเหตุการณ์ด้านความปลอดภัยตามนโยบาย
- หากระบบตรวจสอบสิทธิ์ที่จำเป็นทำงานไม่ได้ ให้ปฏิเสธการเข้าถึงข้อมูลสุขภาพนั้น

# 12. สรุปแนวคิดที่ผมแนะนำ

CRM ของแอปนี้ควรทำหน้าที่เป็น ระบบบริหารความสัมพันธ์และประสานงานการดูแลสุขภาพของครอบครัว โดยมี 5 แกนหลัก:

1. People & Relationships — รู้ว่าใครเป็นใคร และเกี่ยวข้องกันอย่างไร
2. Caregiver & Authorization — รู้ว่าใครได้รับอนุญาตให้ทำอะไร
3. Timeline & Tasks — รู้ว่าเกิดอะไรขึ้นแล้ว และยังต้องดำเนินการอะไร
4. Appointments & Communication — ประสานงานการดูแลให้ต่อเนื่อง
5. Privacy, Consent & Audit — ควบคุมข้อมูลและตรวจสอบย้อนหลังได้

สิ่งสำคัญที่สุดคืออย่าออกแบบให้ CRM เป็นเพียงฐานข้อมูลสมาชิกที่มีสิทธิ์อ่านข้อมูลของกันและกันทั้งหมด แต่ให้ CRM เข้าใจทั้ง ความสัมพันธ์ บริบทของงาน ขอบเขตการมอบหมาย และสิทธิ์เข้าถึงข้อมูลแต่ละประเภท

ขั้นต่อไปที่เหมาะสมคือการนำแนวคิดนี้ไปจัดทำ `CRM_DOMAIN_ARCHITECTURE.md` โดยระบุ Domain Boundary, Entity Relationships, Lifecycle, API Responsibilities และการเชื่อมต่อกับ Authorization Baseline ให้ชัดเจน เพื่อให้ AI Agent นำไปสร้างโค้ดได้โดยไม่ต้องตีความโครงสร้าง CRM เอง
