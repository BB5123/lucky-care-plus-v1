สำหรับแอป Family Health CRM ที่เรากำลังออกแบบอยู่ ผมมองว่าส่วน CRM ควรเป็นหนึ่งในแกนหลักของระบบ ไม่ใช่เพียงหน้าจัดเก็บชื่อ เบอร์โทรศัพท์ หรือลิสต์สมาชิกครอบครัว แต่เป็นระบบที่ช่วยจัดการ ข้อมูลบุคคล ความสัมพันธ์ในครอบครัว การดูแลผู้ป่วย การติดตามงาน และความต่อเนื่องในการดูแลสุขภาพ โดยทำงานร่วมกับระบบจัดเก็บข้อมูลสุขภาพและระบบ AI อย่างมีขอบเขตชัดเจน

สิ่งสำคัญที่สุดคือ ต้องออกแบบให้เป็น Healthcare CRM ไม่ใช่นำ CRM สำหรับงานขายมาเปลี่ยนชื่อเป็นระบบสุขภาพ เพราะวัตถุประสงค์ ข้อมูล และข้อกำหนดด้านสิทธิ์การเข้าถึงแตกต่างกันมาก

# 1. CRM ในแอปนี้มีหน้าที่อะไร?

CRM ย่อมาจาก Customer Relationship Management แต่ในแอปสุขภาพของเรา คำว่า Customer ไม่ได้หมายถึงลูกค้าที่เราต้องขายสินค้าให้เป็นหลัก แต่หมายถึงบุคคลและความสัมพันธ์ที่เกี่ยวข้องกับการดูแลสุขภาพ เช่น ผู้สูงอายุ สมาชิกครอบครัว ผู้ดูแล และทีมดูแลสุขภาพที่ได้รับอนุญาต

CRM จึงควรตอบคำถามสำคัญได้ว่า

- เรากำลังดูแลใคร และบุคคลนั้นมีข้อมูลติดต่ออะไรบ้าง?
- บุคคลนี้เป็นสมาชิกของครอบครัวหรือ Workspace ใด?
- ใครมีหน้าที่ดูแลบุคคลนี้ และมีอำนาจทำอะไรได้บ้าง?
- งานที่ต้องติดตามมีอะไร ใครเป็นผู้รับผิดชอบ และกำหนดเวลาเมื่อไร?
- เคยมีการติดต่อ นัดหมาย ติดตาม หรือดำเนินการอะไรไปแล้วบ้าง?
- เรื่องใดกำลังรอการดำเนินการ และเรื่องใดเสร็จสิ้นแล้ว?
- ระบบสามารถแจ้งเตือนหรือช่วยให้ครอบครัวประสานงานกันได้อย่างไร?
- ข้อมูลแต่ละรายการเปิดเผยให้ใครเห็นได้บ้าง และมีเหตุผลหรืออำนาจใดรองรับ?

เป้าหมายไม่ใช่แค่เก็บข้อมูลให้ครบ แต่ต้องช่วยให้การดูแลดำเนินต่อได้อย่างเป็นระบบ ลดการลืมนัด ลดงานตกหล่น และป้องกันการเปิดเผยข้อมูลสุขภาพแก่บุคคลที่ไม่มีสิทธิ์

# 2. CRM แตกต่างจากระบบข้อมูลสุขภาพอย่างไร?

นี่เป็นการแบ่งขอบเขตที่ควรตัดสินใจตั้งแต่ต้น เพราะถ้ารวมทุกอย่างไว้ใน CRM โดยไม่มีเส้นแบ่งชัดเจน ในอนาคตระบบจะซับซ้อนมากและตรวจสอบสิทธิ์ได้ยาก

## CRM Domain

ดูแลความสัมพันธ์ การประสานงาน และกระบวนการติดตาม

- ข้อมูลบุคคลและช่องทางติดต่อ
- สมาชิกครอบครัวและความสัมพันธ์
- ผู้ดูแลและการมอบหมายอำนาจ
- ประวัติการติดต่อและเหตุการณ์ใน Timeline
- งานติดตามและการนัดหมาย
- การแจ้งเตือนและการประสานงาน

## Health Record Domain

ดูแลข้อมูลสุขภาพจริงและประวัติทางการแพทย์

- ความดันโลหิต น้ำตาล และชีพจร
- รายการยาและประวัติการใช้ยา
- อาการและประวัติสุขภาพ
- โรคประจำตัวและการแพ้ยา
- ผลตรวจและข้อมูลจากอุปกรณ์สุขภาพ
- ข้อมูลการประเมินหรือคำแนะนำทางการแพทย์

## Authorization & Consent Domain

ควบคุมว่าใครเข้าถึงข้อมูลอะไรได้ และภายใต้เงื่อนไขใด

- Permissions และขอบเขตข้อมูล
- ความสัมพันธ์ที่ได้รับการยืนยัน
- สิทธิ์ที่ได้รับมอบหมายและวันหมดอายุ
- Consent และฐานอำนาจทางกฎหมายที่เกี่ยวข้อง
- การเพิกถอนสิทธิ์และ Audit Log

ตัวอย่างเช่น CRM อาจมีรายการว่า “คุณแม่มีนัดติดตามผลวันที่ 28 ตุลาคม” ส่วนรายละเอียดผลตรวจจะอยู่ใน Health Record Domain

CRM อาจแสดงลิงก์ไปยังรายละเอียดผลตรวจได้ แต่ผู้ใช้ต้องผ่านการตรวจสิทธิ์ของข้อมูลผลตรวจนั้นอีกครั้ง ไม่ใช่เพียงมีสิทธิ์อ่าน Timeline แล้วจะอ่านผลตรวจได้ทั้งหมด

หลักการ: CRM ทำหน้าที่ประสานงานและเชื่อมโยงข้อมูล แต่ไม่ได้เป็นช่องทางลัดเพื่อเข้าถึงข้อมูลสุขภาพทั้งหมด

# 3. โมดูล CRM ที่ควรมีในแอป

ผมแนะนำให้แบ่งออกเป็นโมดูลที่มีหน้าที่ชัดเจน ดังนี้

## 3.1 Workspace & Family Management

โมดูลนี้ดูแลพื้นที่ใช้งานของครอบครัวหรือกลุ่มผู้ดูแล

ตัวอย่าง Workspace:

- ครอบครัว A
- บ้านของคุณแม่
- ครอบครัว B
- ทีมดูแลผู้ป่วยที่ได้รับอนุญาต

Workspace เป็นขอบเขตสำหรับจัดการสมาชิก การตั้งค่า และการประสานงาน ไม่ได้หมายความว่าสมาชิกทุกคนสามารถเปิดอ่านข้อมูลสุขภาพของทุกคนใน Workspace ได้

ความสามารถที่ควรมี:

| ความสามารถ          | รายละเอียด                                            |
| ------------------- | ----------------------------------------------------- |
| สร้าง Workspace     | สร้างพื้นที่ครอบครัวหรือพื้นที่ดูแล                   |
| เชิญสมาชิก          | เชิญผ่าน QR Code, Invitation Code หรือช่องทางที่กำหนด |
| จัดการสมาชิก        | เพิ่ม ระงับ หรือถอนสมาชิกตามสิทธิ์                    |
| กำหนดบทบาท          | Owner, Workspace Admin, Member เป็นต้น                |
| ดูสถานะคำเชิญ       | Pending, Accepted, Expired, Revoked                   |
| จัดการการเป็นสมาชิก | วันที่เข้าร่วม วันที่ออก และผู้ดำเนินการ              |
| แยกพื้นที่          | ป้องกันข้อมูลข้าม Workspace โดยไม่ได้รับอนุญาต        |

### ตัวอย่างสำคัญ

ลูกสาวเป็น Workspace Admin จึงสามารถจัดการคำเชิญและสมาชิกในครอบครัวได้ แต่ไม่ได้หมายความว่าลูกสาวจะมีสิทธิ์อ่านผลตรวจ รายการยา หรือข้อมูลส่วนตัวทั้งหมดของคุณแม่โดยอัตโนมัติ

การเข้าถึงข้อมูลสุขภาพต้องพิจารณาสิทธิ์แยกต่างหาก

## 3.2 Person & Contact Management

โมดูลนี้เป็นทะเบียนบุคคลและข้อมูลติดต่อหลักของระบบ

ข้อมูลที่อาจจัดเก็บ ได้แก่

- ชื่อและชื่อที่ต้องการให้เรียก
- วันเกิดหรือช่วงปีเกิดตามความเหมาะสม
- เบอร์โทรศัพท์และอีเมล
- ภาษาที่ต้องการใช้
- ช่องทางติดต่อที่สะดวก
- ผู้ติดต่อฉุกเฉิน
- สถานะการใช้งานบัญชี
- สถานะการยืนยันตัวตน
- ความสัมพันธ์กับ Workspace
- ข้อมูลการตั้งค่าการแจ้งเตือน

ต้องแยกแนวคิด 3 อย่างออกจากกันให้ชัดเจน:

1. User Account — บัญชีที่ใช้เข้าสู่ระบบ
2. Person — ตัวบุคคลที่ระบบรู้จัก
3. Health Profile — ข้อมูลสุขภาพที่ผูกกับบุคคลนั้น

ทั้งสามสิ่งไม่จำเป็นต้องเป็นหนึ่งเดียวกันเสมอไป

ตัวอย่างเช่น คุณแม่อาจมี Health Profile อยู่ในระบบ แต่ยังไม่มีบัญชีสำหรับเข้าสู่ระบบ ลูกสาวอาจเป็นผู้ช่วยจัดตั้งโปรไฟล์โดยไม่มีสิทธิ์เปิดดูข้อมูลทุกประเภทของคุณแม่

การแยกเช่นนี้ยังช่วยรองรับกรณีที่บุคคลหนึ่งมีความสัมพันธ์กับหลาย Workspace หรือมีการเปลี่ยนผู้ดูแลในอนาคต

## 3.3 Relationship Management

นี่เป็นโมดูลสำคัญของ Healthcare CRM เพราะระบบต้องรู้ว่าบุคคลต่าง ๆ เกี่ยวข้องกันอย่างไร ไม่ใช่เพียงใครอยู่ในรายชื่อสมาชิก

ความสัมพันธ์ที่อาจรองรับ ได้แก่

- พ่อ แม่ ลูก
- คู่สมรส
- พี่น้อง
- ญาติ
- ผู้ดูแลที่ไม่ใช่ญาติ
- ผู้แทนที่ได้รับมอบอำนาจ
- ผู้ติดต่อฉุกเฉิน
- ผู้ดูแลหลักและผู้ดูแลสำรอง

แต่ต้องแยก ความสัมพันธ์ทางครอบครัว ออกจาก อำนาจในการเข้าถึงข้อมูล

| ความสัมพันธ์หรือสถานะ          | สิ่งที่บอกระบบ                 | สิ่งที่ไม่ได้รับโดยอัตโนมัติ     |
| ------------------------------ | ------------------------------ | -------------------------------- |
| ลูกสาว                         | ความสัมพันธ์กับคุณแม่          | สิทธิ์อ่านข้อมูลสุขภาพทั้งหมด    |
| ผู้ติดต่อฉุกเฉิน               | ช่องทางติดต่อกรณีฉุกเฉิน       | สิทธิ์เปิดประวัติการรักษา        |
| ผู้ดูแลหลัก                    | บทบาทในการประสานงาน            | อำนาจทำทุกอย่างแทนผู้ป่วย        |
| ผู้รับมอบอำนาจที่ผ่านการยืนยัน | ขอบเขตอำนาจตามหลักฐานและนโยบาย | สิทธิ์เกินขอบเขตที่ได้รับ        |
| ผู้ทำงานติดตาม                 | งานที่ได้รับมอบหมาย            | สิทธิ์เข้าถึงข้อมูลสุขภาพทั้งหมด |

ตัวอย่างเช่น บุคคล A เป็นลูกสาวของคุณแม่ แต่คุณแม่อาจอนุญาตให้ลูกสาวดูข้อมูลความดันโลหิตและช่วยจัดการนัดหมาย โดยไม่อนุญาตให้เปิดดูบันทึกสุขภาพบางประเภท

ระบบจึงต้องจัดการทั้งความสัมพันธ์และสิทธิ์ที่แยกจากกัน

## 3.4 Caregiver & Delegation Management

โมดูลนี้ดูแลว่าบุคคลใดได้รับอนุญาตให้ช่วยดูแลใคร และทำอะไรได้บ้าง

ข้อมูลที่ควรมีในการมอบหมายสิทธิ์ เช่น

- ผู้ให้สิทธิ์
- ผู้รับสิทธิ์
- บุคคลเจ้าของข้อมูลที่เกี่ยวข้อง
- ขอบเขตการดำเนินการ
- ประเภทข้อมูลที่เข้าถึงได้
- วันเริ่มต้นและวันสิ้นสุด
- สถานะการยืนยัน
- สถานะการเพิกถอน
- ข้อจำกัดหรือเงื่อนไขการใช้สิทธิ์
- หลักฐานหรือที่มาของอำนาจที่เกี่ยวข้อง
- ประวัติการเปลี่ยนแปลง

ตัวอย่างสิทธิ์ที่อาจมอบหมาย:

- ดูข้อมูลสุขภาพบางหมวด
- บันทึกค่าความดันโลหิตแทนเจ้าของโปรไฟล์
- ช่วยจัดการนัดหมาย
- จัดการรายการเตือนความจำ
- ดูงานดูแลที่ได้รับมอบหมาย
- รับการแจ้งเตือนในขอบเขตที่อนุญาต

ต้องแยกสิทธิ์ในการอ่าน การเพิ่ม การแก้ไข การส่งออก และการแชร์ข้อมูลออกจากกัน ไม่ควรให้สิทธิ์กว้างเกินความจำเป็น

การมีชื่อเป็นผู้ดูแลเพียงอย่างเดียวไม่ถือเป็นหลักฐานว่ามีอำนาจตามกฎหมายในการตัดสินใจแทนผู้ป่วยทุกเรื่อง

## 3.5 Care Timeline & Interaction History

นี่คือหนึ่งในส่วนที่ทำให้ CRM มีประโยชน์กว่าทะเบียนสมาชิกทั่วไป

Timeline รวมเหตุการณ์ที่เกี่ยวข้องกับการดูแลไว้ตามลำดับเวลา เช่น

- เพิ่มสมาชิกเข้าระบบ
- เชิญผู้ดูแล
- เปลี่ยนแปลงสิทธิ์
- จัดเตรียมนัดหมาย
- โทรติดตามหรือบันทึกการติดต่อ
- สร้างงานติดตามสุขภาพ
- บันทึกว่าได้ช่วยเหลือในเรื่องใด
- ได้รับแจ้งเตือนและดำเนินการต่อ
- เชื่อมโยงไปยังเหตุการณ์สุขภาพที่เกี่ยวข้อง

แต่ Timeline ไม่ควรเก็บข้อมูลทั้งหมดซ้ำซ้อนอีกชุดหนึ่ง

ตัวอย่าง:

| เหตุการณ์ใน CRM             | ข้อมูลต้นทางที่เกี่ยวข้อง        |
| --------------------------- | -------------------------------- |
| นัดติดตามผลวันที่ 28 ต.ค.   | Appointment                      |
| ได้รับมอบหมายให้ตรวจความดัน | Care Task                        |
| วัดความดันแล้ว              | Health Measurement               |
| บันทึกการติดต่อกับผู้ดูแล   | Interaction Log                  |
| ผู้ดูแลถูกเพิกถอนสิทธิ์     | Delegation / Authorization Audit |

แนวทางนี้ทำให้ระบบสามารถเชื่อมโยงข้อมูลที่เกี่ยวข้องกันได้ โดยยังคงแยกการจัดเก็บและสิทธิ์เข้าถึงตามประเภทข้อมูล

ข้อควรระวัง: หาก Timeline แสดงข้อมูลสุขภาพ ระบบต้องตรวจสิทธิ์ของข้อมูลแต่ละรายการก่อนแสดงผล ห้ามถือว่าผู้ที่อ่าน Timeline ได้จะอ่านเหตุการณ์และรายละเอียดทุกอย่างใน Timeline ได้ด้วย

## 3.6 Care Task & Follow-up Management

โมดูลนี้ช่วยให้ครอบครัวและผู้ดูแลรู้ว่าอะไรต้องทำ ใครรับผิดชอบ และเมื่อใดต้องดำเนินการ

ตัวอย่างงาน:

- ช่วยคุณแม่วัดความดันในวันพรุ่งนี้
- ตรวจสอบว่ามีการรับประทานยาตามแผนที่บันทึกไว้หรือไม่
- เตรียมเอกสารก่อนไปพบแพทย์
- ติดตามหลังการนัดหมาย
- ติดต่อผู้ดูแลหลักเพื่อยืนยันการดำเนินการ
- ตรวจสอบว่าอุปกรณ์สุขภาพยังส่งข้อมูลตามปกติ

สถานะงานอาจประกอบด้วย

`Open → In Progress → Waiting → Completed`

และอาจมีสถานะ `Cancelled` หรือ `Overdue` สำหรับงานที่ยกเลิกหรือล่วงเลยกำหนด

แต่ละงานควรมีข้อมูลอย่างน้อยดังนี้

| ฟิลด์               | ความหมาย                                    |
| ------------------- | ------------------------------------------- |
| Task ID             | รหัสงาน                                     |
| Subject             | หัวข้องาน                                   |
| Related Person      | บุคคลที่เกี่ยวข้อง                          |
| Assigned To         | ผู้รับผิดชอบ                                |
| Due At              | กำหนดเวลา                                   |
| Status              | สถานะ                                       |
| Priority            | ระดับความสำคัญ                              |
| Created By          | ผู้สร้างงาน                                 |
| Completion Evidence | หลักฐานหรือรายละเอียดเมื่อทำเสร็จ ถ้าจำเป็น |
| Visibility Scope    | ขอบเขตผู้มีสิทธิ์เห็นงาน                    |

จุดที่สำคัญต่อระบบสิทธิ์คือ การได้รับมอบหมายงานไม่ได้แปลว่าได้รับสิทธิ์เข้าถึงข้อมูลสุขภาพของผู้ป่วยทั้งหมด

ตัวอย่างเช่น ผู้ดูแลสำรองได้รับงานให้เตือนเรื่องนัดหมาย เขาควรเห็นรายละเอียดที่จำเป็นต่อการทำงานนั้น แต่ไม่จำเป็นต้องเห็นประวัติการแพ้ยาหรือบันทึกสุขภาพทุกหมวด

หากงานใดต้องอาศัยข้อมูลสุขภาพเฉพาะ ระบบต้องให้สิทธิ์ข้อมูลส่วนนั้นเพิ่มเติมอย่างชัดเจน

## 3.7 Appointment & Care Coordination

โมดูลนี้จัดการการประสานงานและนัดหมาย ไม่ควรถือว่าการมีนัดหมายเท่ากับการมีเวชระเบียนของการพบแพทย์ครั้งนั้น

สิ่งที่อาจมี ได้แก่

- วันและเวลานัด
- สถานพยาบาลหรือผู้ให้บริการ
- วัตถุประสงค์ของนัด
- ผู้ประสานงาน
- ผู้ที่จะไปพบแพทย์ด้วย
- สถานะการยืนยันนัด
- สถานะการเข้าร่วม
- เอกสารที่ต้องเตรียม
- งานติดตามหลังนัด
- การเลื่อนหรือยกเลิกนัด

ตัวอย่างสถานะ:

`Planned → Confirmed → Attended`

และอาจมี `Rescheduled`, `Cancelled`, `Missed` หรือ `Needs Follow-up`

เมื่อการนัดหมายเสร็จสิ้น ระบบอาจสร้างงานติดตามต่อ เช่น เตือนให้บันทึกผลตรวจ หรือให้ผู้ดูแลตรวจสอบว่ามีการดำเนินการตามคำแนะนำที่ได้รับแล้วหรือไม่

ข้อมูลทางการแพทย์ที่เกิดจากการนัดหมายควรอยู่ในส่วนข้อมูลสุขภาพที่เหมาะสม โดย CRM เชื่อมโยงอ้างอิงตามสิทธิ์ที่มีอยู่

## 3.8 Communication & Notification Management

CRM ควรรองรับการสื่อสารที่เกี่ยวข้องกับการดูแล เช่น

- การเชิญสมาชิก
- การแจ้งเตือนนัดหมาย
- การแจ้งเตือนงานที่ได้รับมอบหมาย
- การแจ้งว่างานเลยกำหนด
- การแจ้งเปลี่ยนแปลงสิทธิ์
- การยืนยันหรือยกเลิกการนัดหมาย
- การแจ้งเตือนผู้ดูแลสำรองตามกฎที่กำหนด

ในระยะเริ่มต้นอาจไม่จำเป็นต้องสร้างระบบแชตเต็มรูปแบบ แต่ควรออกแบบ Notification และการติดตามสถานะการส่งให้ดีตั้งแต่ต้น

ข้อมูลที่ใช้ส่งการแจ้งเตือนควรมีขอบเขตด้วย เช่น หน้าจอล็อกโทรศัพท์ไม่ควรแสดงรายละเอียดสุขภาพที่อ่อนไหวโดยไม่จำเป็น การแจ้งเตือนอาจเขียนว่า “มีรายการสุขภาพที่ต้องตรวจสอบ” แล้วให้ผู้ใช้เข้าสู่ระบบเพื่ออ่านรายละเอียดหลังตรวจสิทธิ์แล้ว

นอกจากนี้ การมีสิทธิ์รับแจ้งเตือนไม่ได้หมายความว่าผู้รับมีสิทธิ์เปิดดูข้อมูลต้นทางของการแจ้งเตือนเสมอไป

## 3.9 Consent & Communication Preferences

โมดูลนี้บันทึกการให้ความยินยอมและความต้องการในการติดต่อ แต่ต้องไม่รวมทุกเรื่องไว้ในช่อง `consent = true` ช่องเดียว

ข้อมูลควรแยกอย่างน้อยเป็น

- ประเภทความยินยอม
- วัตถุประสงค์
- ผู้ให้ความยินยอม
- บุคคลที่ข้อมูลเกี่ยวข้อง
- วันที่ให้ความยินยอม
- รุ่นของข้อความหรือเอกสารที่ยอมรับ
- ขอบเขตข้อมูลหรือกิจกรรมที่เกี่ยวข้อง
- สถานะการถอนความยินยอม
- หลักฐานการให้ความยินยอมตามความเหมาะสม

ขณะเดียวกัน Communication Preferences ใช้เก็บว่าผู้ใช้สะดวกให้ติดต่อผ่านช่องทางใด ภาษาอะไร และต้องการรับการแจ้งเตือนแบบใด

ทั้งสองส่วนไม่ใช่สิ่งเดียวกัน:

- การตั้งค่าว่าไม่ต้องการรับ SMS ไม่ได้แปลว่าถอนความยินยอมทุกประเภท
- การยินยอมให้รับการแจ้งเตือน ไม่ได้แปลว่ายินยอมให้ผู้ดูแลทุกคนเข้าถึงข้อมูลสุขภาพ
- การมอบสิทธิ์ในระบบ ไม่ได้ใช้แทนการพิจารณาฐานอำนาจทางกฎหมายที่จำเป็น

## 3.10 Case & Service Request Management

โมดูลนี้จัดการเรื่องที่ต้องมีผู้รับผิดชอบและติดตามจนจบ โดยไม่จำเป็นต้องเป็นปัญหาทางการแพทย์เสมอไป

ตัวอย่าง:

- สมาชิกไม่สามารถเข้าสู่ระบบ
- ต้องยืนยันตัวตนผู้ดูแล
- ต้องแก้ไขข้อมูลติดต่อ
- ต้องตรวจสอบคำเชิญที่ไม่สำเร็จ
- ต้องดำเนินการคำขอถอนสิทธิ์
- ต้องขอสำเนาข้อมูลหรือดำเนินการตามคำขอของเจ้าของข้อมูล

แต่ละ Case ควรมีผู้รับผิดชอบ สถานะ เส้นตาย ประวัติการดำเนินการ และขอบเขตผู้ที่เปิดดูได้

หากมีรายละเอียดสุขภาพอยู่ใน Case ต้องควบคุมสิทธิ์ตามความอ่อนไหวของข้อมูลนั้น ไม่ควรถือว่าผู้ดูแล Case ทุกคนเห็นข้อมูลสุขภาพได้

## 3.11 Document & Attachment Management

CRM อาจต้องรองรับเอกสารที่ใช้ประสานงาน เช่น เอกสารนัดหมาย แบบฟอร์ม หรือเอกสารยืนยันอำนาจของผู้แทน

แต่ต้องแยกประเภทเอกสารและระดับความอ่อนไหว เช่น

- เอกสารทั่วไปของ Workspace
- เอกสารยืนยันตัวตนหรืออำนาจผู้แทน
- เอกสารนัดหมาย
- เอกสารสุขภาพ
- เอกสารที่ต้องจำกัดการดาวน์โหลดหรือการแชร์

การดูไฟล์ ดาวน์โหลดไฟล์ แชร์ไฟล์ และลบไฟล์ควรเป็นคนละสิทธิ์ตามความเหมาะสม

ระบบควรตรวจสิทธิ์อีกครั้งเมื่อมีการขอดาวน์โหลด และเมื่อมีการส่งไฟล์ผ่านลิงก์ที่มีวันหมดอายุ การเพิกถอนสิทธิ์ต้องไม่ทำให้ผู้ใช้ยังเข้าถึงไฟล์ได้โดยอ้อมผ่านลิงก์เดิมโดยไม่มีข้อจำกัด

## 3.12 CRM Dashboard & Care Overview

Dashboard เป็นหน้าสรุปเพื่อช่วยให้ผู้ดูแลเห็นงานที่ต้องดำเนินการ โดยแสดงเฉพาะข้อมูลที่ผู้ใช้มีสิทธิ์เห็น

ตัวอย่างองค์ประกอบ:

- งานที่ต้องทำวันนี้
- งานเกินกำหนด
- นัดหมายที่กำลังจะมาถึง
- งานที่รอการยืนยัน
- รายการติดตามที่ยังไม่เสร็จ
- สถานะการเชิญสมาชิก
- คำขอที่รอการตรวจสอบ
- สถานะของผู้ดูแลและสิทธิ์ที่ใกล้หมดอายุ

ควรระวังไม่ใช้ Dashboard เป็นช่องทางที่รวมข้อมูลทั้งหมดแล้วแสดงให้ผู้ใช้ทุกบทบาทเห็นเหมือนกัน

ข้อมูลสรุปยังต้องผ่านการตรวจสิทธิ์ เช่น จำนวนงานติดตามอาจแสดงได้ แต่ชื่อบุคคล รายละเอียดสุขภาพ หรือผลตรวจต้องแสดงเฉพาะเมื่อมีสิทธิ์รองรับ

# 4. ผู้ใช้แต่ละประเภทควรใช้ CRM ได้อย่างไร?

ผมแนะนำให้เริ่มจากบทบาทเชิงธุรกิจที่ชัดเจน แล้วใช้ Permission Catalog ควบคุมสิทธิ์จริง แทนการให้สิทธิ์ตามชื่อ Role เพียงอย่างเดียว

| บทบาท                   | หน้าที่หลัก                                 | ขอบเขตที่ต้องระวัง                                |
| ----------------------- | ------------------------------------------- | ------------------------------------------------- |
| Profile Owner           | จัดการข้อมูลและสิทธิ์ของตนเอง               | สิทธิ์ของผู้อื่นต้องไม่เกิดขึ้นโดยอัตโนมัติ       |
| Workspace Owner         | ดูแลพื้นที่ครอบครัวและสมาชิก                | ไม่ได้สิทธิ์ข้อมูลสุขภาพของทุกคนโดยอัตโนมัติ      |
| Workspace Admin         | จัดการสมาชิก คำเชิญ และการตั้งค่า           | ไม่ใช่ผู้ดูแลสุขภาพโดยอัตโนมัติ                   |
| Caregiver               | ช่วยประสานงานตามที่ได้รับอนุญาต             | ใช้สิทธิ์เฉพาะข้อมูลและงานที่ได้รับมอบหมาย        |
| Task Assignee           | ดำเนินงานที่ได้รับมอบหมาย                   | ไม่ได้สิทธิ์เข้าถึงโปรไฟล์ทั้งหมด                 |
| Verified Representative | ดำเนินการตามอำนาจที่ได้รับการยืนยัน         | อำนาจต้องมีขอบเขตและไม่เกินหลักฐานหรือกฎที่รองรับ |
| Healthcare Professional | ให้บริการตามสิทธิ์และหน้าที่ที่ได้รับอนุญาต | ต้องมีการยืนยันตัวตนและขอบเขตการเข้าถึงแยกต่างหาก |
| Platform Support        | ช่วยเหลือด้านเทคนิค                         | ไม่ควรมีสิทธิ์ประจำในการอ่านข้อมูลสุขภาพ          |

บทบาทเหล่านี้ไม่จำเป็นต้องสร้างครบทุกบทบาทใน MVP โดยเฉพาะสิทธิ์สำหรับบุคลากรทางการแพทย์ ควรกำหนดขอบเขตแยก หากยังไม่มีรูปแบบการให้บริการที่ชัดเจน

# 5. ตัวอย่างการทำงานร่วมกันของ CRM และ Health Record

สมมติว่าคุณแม่ใช้แอปติดตามสุขภาพ ลูกสาวช่วยดูแล และมีสมาชิกอีกคนเป็นผู้ดูแลสำรอง

ขั้นที่ 1 — สร้างพื้นที่ครอบครัว

ลูกสาวสร้าง Workspace และเชิญคุณแม่ ระบบบันทึกสมาชิกและความสัมพันธ์ แต่ยังไม่ให้สิทธิ์เข้าถึงข้อมูลสุขภาพทุกประเภทโดยอัตโนมัติ

ขั้นที่ 2 — กำหนดขอบเขตการดูแล

คุณแม่หรือผู้มีอำนาจที่ผ่านการตรวจสอบ อนุญาตให้ลูกสาวอ่านข้อมูลบางหมวดและช่วยจัดการงานบางประเภท ระบบบันทึกขอบเขตและสถานะสิทธิ์

ขั้นที่ 3 — สร้างงานและติดตาม

CRM สร้างงานให้วัดความดันหรือเตรียมตัวก่อนพบแพทย์ ระบุผู้รับผิดชอบและกำหนดเวลา โดยจำกัดรายละเอียดที่ผู้รับงานมองเห็น

ขั้นที่ 4 — บันทึกข้อมูลสุขภาพ

ข้อมูลความดันที่วัดได้ถูกจัดเก็บใน Health Record Domain และเชื่อมโยงกับงานใน CRM ตามความเหมาะสม ไม่จำเป็นต้องเก็บข้อมูลซ้ำในหลายที่

ขั้นที่ 5 — ติดตามและตรวจสอบย้อนหลัง

Timeline แสดงว่ามีการสร้างงาน ดำเนินงาน และบันทึกข้อมูลเมื่อใด ส่วนการเปิดดูข้อมูลสุขภาพจริงต้องผ่านการตรวจสิทธิ์ของข้อมูลนั้น

ตัวอย่างนี้แสดงให้เห็นว่า CRM เป็นตัวประสานงานระหว่างคน งาน และข้อมูล แต่สิทธิ์เข้าถึงข้อมูลสุขภาพยังถูกควบคุมแยกตามหลักการที่เราวางไว้

# 6. ข้อมูลหลักที่ควรมีใน CRM Domain

ด้านล่างเป็นชุด Entity ที่แนะนำในระดับออกแบบโดเมน ไม่ใช่การบังคับว่าต้องสร้างตารางทั้งหมดตั้งแต่วันแรก

| Entity                      | หน้าที่                                   |
| --------------------------- | ----------------------------------------- |
| `workspaces`                | พื้นที่ครอบครัวหรือทีมดูแล                |
| `workspace_memberships`     | ความเป็นสมาชิกและบทบาทใน Workspace        |

หนึ่ง — อย่าฝังสิทธิ์ทั้งหมดไว้ใน Membership

`workspace_memberships` บอกว่าใครเป็นสมาชิกและมีบทบาทอะไรในพื้นที่นั้น แต่สิทธิ์อ่านข้อมูลสุขภาพของแต่ละบุคคลต้องพิจารณาจากกฎเฉพาะอีกชั้นหนึ่ง

สอง — อย่าเก็บข้อมูลสุขภาพซ้ำใน Interaction Log โดยไม่จำเป็น

หากจำเป็นต้องบันทึกข้อความอิสระ ให้ถือว่าข้อความนั้นอาจมีข้อมูลสุขภาพอ่อนไหว และกำหนดระดับการเข้าถึง การเก็บรักษา และการตรวจสอบอย่างเหมาะสม

สาม — Timeline ต้องไม่กลายเป็นช่องทางข้ามสิทธิ์

ถ้ารายการ Timeline เชื่อมไปยังข้อมูลที่มีข้อจำกัด การเข้าถึงรายละเอียดต้นทางต้องตรวจสิทธิ์ใหม่เสมอ

สี่ — ระวังการเพิกถอนสิทธิ์และงานที่ทำงานภายหลัง

# 7. กฎด้านสิทธิ์ที่ CRM ต้องบังคับใช้อย่างเคร่งครัด

แนวทางต่อไปนี้สอดคล้องกับ Authorization Baseline ที่เรากำลังตรึงไว้

1. Workspace membership is not health access. เป็นสมาชิกไม่ได้หมายความว่าอ่านข้อมูลสุขภาพได้
2. Admin is not automatic health access. ผู้ดูแล Workspace ไม่ได้สิทธิ์ข้อมูลสุขภาพเพียงเพราะมีบทบาท Admin
3. Task assignment is not health access. ได้รับมอบหมายงานไม่ได้หมายความว่าอ่านข้อมูลสุขภาพทั้งหมดได้
4. Relationship is not authority. การเป็นพ่อแม่ ลูก คู่สมรส หรือผู้ติดต่อฉุกเฉิน ไม่ได้ให้อำนาจเข้าถึงข้อมูลทั้งหมดโดยอัตโนมัติ
5. Read is not export or share. อ่านได้ไม่ได้แปลว่าส่งออก ดาวน์โหลด หรือแชร์ต่อได้
6. Delegated authority cannot exceed the grantor’s authority. ผู้มอบสิทธิ์ไม่สามารถมอบสิทธิ์เกินขอบเขตที่ตนมี
7. Revocation must take effect across access paths. เมื่อเพิกถอนสิทธิ์ ต้องพิจารณา API, Cache, งานในคิว และลิงก์ไฟล์ที่ออกไปแล้ว
8. Fail closed for protected health data. ถ้าระบบตรวจสอบสิทธิ์ที่จำเป็นไม่ได้ ต้องไม่เปิดเผยข้อมูลสุขภาพนั้น
9. Platform staff have no standing health data access. เจ้าหน้าที่แพลตฟอร์มไม่ควรมีสิทธิ์อ่านข้อมูลสุขภาพของผู้ใช้เป็นสิทธิ์ประจำ
10. Audit meaningful actions. การเปลี่ยนสิทธิ์ อ่านข้อมูลอ่อนไหว ส่งออก แชร์ และดำเนินการสำคัญอื่น ๆ ต้องมีการตรวจสอบย้อนหลังตามนโยบาย

นอกจากนี้ ต้องแยกการให้ความยินยอม การมีฐานอำนาจทางกฎหมาย และการอนุญาตผ่านระบบออกจากกัน ทั้งสามเรื่องเกี่ยวข้องกัน แต่ไม่ใช่สิ่งเดียวกัน

# 9. ควรพัฒนาอะไรเป็น MVP ก่อน?

ไม่แนะนำให้สร้าง CRM ทุกโมดูลพร้อมกัน เพราะจะเพิ่มทั้งจำนวนหน้าจอ รูปแบบข้อมูล และจำนวนกฎ Authorization ที่ต้องทดสอบ

ผมแนะนำให้แบ่งดังนี้

Phase 1

Core CRM Foundation

- Workspace และสมาชิก
- Person & Contact
- Relationship
- Caregiver Assignment และ Delegation
- Permission Integration
- Care Task และ Follow-up ขั้นพื้นฐาน
- Timeline ขั้นพื้นฐาน
- Audit Log
- การเพิกถอนสิทธิ์และการตรวจสอบสิทธิ์ซ้ำ

Phase 2

Care Coordination

- Appointment Management
- Notification Center
- Interaction Log
- Document Reference
- งานติดตามหลังนัด
- การประสานงานผู้ดูแลหลายคน

Phase 3

Advanced CRM & AI Integration

- Care Case Management ที่ละเอียดขึ้น
- Care Team และการประสานงานกับสถานพยาบาล
- รายงานการดำเนินงานและตัวชี้วัด
- AI ช่วยสรุป Timeline ที่ผู้ใช้มีสิทธิ์เข้าถึง
- AI ช่วยจัดลำดับงานติดตาม
- การวิเคราะห์ความต่อเนื่องของการดูแล

แม้จะพัฒนาเป็น Phase 1 แต่ไม่ควรเลื่อนการออกแบบ Permission, Consent และ Audit ไปจนถึง Phase หลัง เพราะสิ่งเหล่านี้เป็นรากฐานของข้อมูลที่เกี่ยวข้องกับสุขภาพ

## 10. สิ่งที่ไม่ควรนำมารวมใน CRM โดยตรง

เพื่อป้องกันการขยายขอบเขตจนควบคุมยาก ผมแนะนำให้แบ่งหน้าที่ดังนี้

| เรื่อง                               | Domain ที่ควรเป็นเจ้าของ   |
| ------------------------------------ | -------------------------- |
| ข้อมูลบุคคลและการติดต่อ              | CRM / Identity             |
| Workspace และสมาชิก                  | Workspace                  |
| ความสัมพันธ์และผู้ดูแล               | CRM / Relationship         |
| สิทธิ์และการมอบอำนาจ                 | Authorization              |
| ความยินยอม                           | Consent                    |
| งานติดตามและนัดหมาย                  | CRM / Care Coordination    |
| ค่าความดัน น้ำตาล ชีพจร              | Health Record              |
| โรคประจำตัวและการแพ้ยา               | Health Record              |
| ข้อมูลยาและประวัติการใช้ยา           | Medication / Health Record |
| การประเมินความเสี่ยงและ Safety Guard | AI Safety / Medical Domain |
| การสร้างและกำหนดเส้นทางคำขอ AI       | AI Orchestration           |
| การติดตามต้นทุนและโควตา AI           | AI Usage / Cost            |
| ประวัติการเข้าถึงข้อมูลสำคัญ         | Audit / Security           |

CRM ยังเชื่อมโยงข้อมูลเหล่านี้ได้ แต่ไม่ควรรับผิดชอบเก็บและตัดสินใจกฎทั้งหมดแทน Domain เจ้าของข้อมูล

แผนภาพนี้เป็นแนวแบ่งความรับผิดชอบในระดับโดเมน ไม่ได้หมายความว่าต้องมีฐานข้อมูลหรือบริการแยกกันทุกตัว

สิ่งที่ควรบังคับใช้ใน API ได้แก่

- ทุกคำขอต้องตรวจ Workspace และเจ้าของ Resource ให้ตรงกัน
- ตรวจ Permission และ Scope ก่อนอ่านหรือแก้ไขข้อมูล
- ตรวจสถานะความสัมพันธ์ การมอบสิทธิ์ การหมดอายุ และการเพิกถอน
- ตรวจ Consent หรือฐานอำนาจที่จำเป็นสำหรับกิจกรรมที่เกี่ยวข้อง
- ตรวจสิทธิ์อีกครั้งเมื่องานในคิวจะทำงานจริง หรือก่อนส่งไฟล์ให้ผู้ใช้
- ป้องกันการเดา ID เพื่อเข้าถึงข้อมูลของบุคคลอื่น
- บันทึกเหตุการณ์ด้านความปลอดภัยตามนโยบาย
- หากระบบตรวจสอบสิทธิ์ที่จำเป็นทำงานไม่ได้ ให้ปฏิเสธการเข้าถึงข้อมูลสุขภาพนั้น

# 12. สรุปแนวคิดที่ผมแนะนำ

CRM ของแอปนี้ควรทำหน้าที่เป็น ระบบบริหารความสัมพันธ์และประสานงานการดูแลสุขภาพของครอบครัว โดยมี 5 แกนหลัก:

1. People & Relationships — รู้ว่าใครเป็นใคร และเกี่ยวข้องกันอย่างไร
2. Caregiver & Authorization — รู้ว่าใครได้รับอนุญาตให้ทำอะไร
3. Timeline & Tasks — รู้ว่าเกิดอะไรขึ้นแล้ว และยังต้องดำเนินการอะไร
4. Appointments & Communication — ประสานงานการดูแลให้ต่อเนื่อง
5. Privacy, Consent & Audit — ควบคุมข้อมูลและตรวจสอบย้อนหลังได้

สิ่งสำคัญที่สุดคืออย่าออกแบบให้ CRM เป็นเพียงฐานข้อมูลสมาชิกที่มีสิทธิ์อ่านข้อมูลของกันและกันทั้งหมด แต่ให้ CRM เข้าใจทั้ง ความสัมพันธ์ บริบทของงาน ขอบเขตการมอบหมาย และสิทธิ์เข้าถึงข้อมูลแต่ละประเภท

ขั้นต่อไปที่เหมาะสมคือการนำแนวคิดนี้ไปจัดทำ `CRM_DOMAIN_ARCHITECTURE.md` โดยระบุ Domain Boundary, Entity Relationships, Lifecycle, API Responsibilities และการเชื่อมต่อกับ Authorization Baseline ให้ชัดเจน เพื่อให้ AI Agent นำไปสร้างโค้ดได้โดยไม่ต้องตีความโครงสร้าง CRM เอง
